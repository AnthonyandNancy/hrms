[Heading 1] 01. 项目定位与调研结论
[Heading 2] 1.1 建设定位
[First Paragraph] 建设一套面向企业内部管理的、可长期维护与二次开发的通用型 HRMS：以“员工档案”为数据主线，以“组织与岗位”为结构主线，以“权限与审批”为安全主线，连接招聘、入职、转正、调岗、合同、考勤、假勤、薪酬、绩效、培训、离职和分析报表。
[Body Text] 与“静态页面集合”不同，所有页面必须接入实际 API、数据表、权限规则、状态流转和审计日志；严禁仅为了演示效果在生产业务代码中硬编码假数据。

[Heading 2] 1.3 行业功能参照
[First Paragraph] BambooHR 的公开功能体系包括员工信息、招聘与入职、工资福利、时间与考勤、绩效、分析与合规；Zoho People 包括核心人事、考勤休假、绩效、招聘、薪资集成、报表以及移动端服务。这说明企业级 HRMS 的常规范围已经超出基础“员工 CRUD”。
[Body Text] 技术设计上，NIST 的 RBAC 参考模型支持围绕角色组织权限；OWASP 明确要求默认拒绝、最小权限以及每次请求的服务端权限验证。因此，前端显示控制只是体验层，不能代替后端授权。
[Heading 2] 1.4 建设原则
[Compact] 一个人员主档案： 员工唯一 ID 永不复用；入转调离写履历，不反复覆盖历史。
[Compact] 一个权限中心： 所有模块共用同一用户、角色、资源、数据范围及字段权限模型。
[Compact] 审批与业务解耦： 请假、加班、出差、合同等模块调用同一审批服务，但保留业务实体及状态机。
[Compact] 配置优先： 假期类型、班次、工资项目、绩效模板、审批流程使用配置而非硬编码。
[Compact] 安全默认拒绝： 未授权不可见、不可访问、不可查询、不可导出。
[Compact] 历史可追溯： 员工所属部门、岗位、合同、薪资单、审批单、绩效记录均可追踪变更。
[Compact] 既可单公司运行，又能扩展集团： 初次部署以单企业为目标，数据库预留 company_id，跨公司访问必须再次授权。
[Compact] 一次性范围完整交付： 可按模块顺序开发，但全部 V1.0 的业务闭环都须验收后才能上线。

[Block Text] 一个用户可以关联多个角色；“职务/岗位”是人事业务数据，“系统角色”是授权数据，二者不能简单画等号。部门经理可根据岗位自动建议分配角色，但仍需经过授权流程。
[Heading 2] 2.2 组织模型
[Compact] 公司（Company）→ 部门（Department，支持树形与有效期）→ 岗位（Position）→ 员工（Employee）。
[Compact] 用户账号（User）与员工（Employee）为 1:0..1 关联，候选人尚未成为员工时不强制创建账号。
[Compact] 员工的任职信息独立于自然人档案，支持同员工转岗、借调、跨公司调动和历史追溯。
[Compact] 组织负责人、部门主管、直属上级需要明确的员工 ID 与有效时间；不允许仅依赖“名字”关联。
[Compact] 每个组织单元可配置是否参与人事统计、是否为虚拟部门、是否启用及排序。
[Heading 2] 2.3 V1.0 内含与可选外部系统
[First Paragraph] 内含： PC 管理端 + 响应式员工自助端、所有本书列出的核心业务模块、完整权限体系、基础审批、导入导出、通知、日志与 Docker 部署。
[Body Text] 适配接口但不强制接入： 企业微信单点登录/通知、钉钉、飞书、门禁/指纹/人脸打卡设备、税务申报、银行代发、电子签章、ERP/财务系统。第三方实际接入必须获得对方 API 文档、凭据与授权，不能用模拟调用冒充集成成功。
[Body Text] 不建议在本版自行开发： 国家/地区税务申报平台、银行清算系统、人脸识别算法、完整通用 BPMN 设计器、对外多租户 SaaS 计费；但设计扩展点，保证未来可集成。

[Heading 2] 3.3 典型关键字段
[First Paragraph] 员工档案： 员工编号、姓名、工号、姓名拼音（可选）、手机/邮箱、入职日期、出生日期、在职状态、性别（可选/统计用途需必要性评估）、身份证件种类与编号（仅必要场景）、所属公司/部门/岗位、直属上级、用工类型、转正日期、紧急联系人（受限）、合同关联、银行卡信息（仅薪资需要且额外保护）。
[Body Text] 合同： 合同号、版本、员工、签订日期、起止日期、合同类型、试用约定、续签关联、文件与签署状态、预警状态。
[Body Text] 考勤： 员工、打卡来源、设备流水号、原始时间、标准化时间、地点（仅确有必要时）、班次、考勤日、异常标志、修正记录。
[Body Text] 工资： 员工、月份、批次、项目明细、应发/扣减/实发、币种、计算规则版本、核算状态、审批人、锁定时间、发放确认时间。不要在日志里保存工资明文。
[Heading 1] 04. 权限体系：最高优先级需求
[Heading 2] 4.1 权限模型
[First Paragraph] 推荐 RBAC + Resource/Action + Scoped Grant + Field Policy + Ownership：
[Source Code] 用户 User
  └─ 用户角色 UserRole (company_id, 生效期)
       └─ 角色 Role
            └─ 授权项 RoleGrant
                 ├─ 权限资源 Permission：菜单 / 页面 / 操作 / API能力
                 ├─ 数据范围 DataScope：本人 / 本部门 / 本部门及下级 / 指定部门 / 本公司 / 自定义
                 └─ 条件 Condition：仅在职 / 仅本人发起 / 有效期等

读取/导出敏感字段还需独立 FieldPolicy 检查。
[First Paragraph] 不要把“员工任职岗位 ID”作为权限角色，也不要仅在前端写 if(role==='admin')。权限标识按资源与动作稳定命名：hr.employee.read、hr.employee.create、hr.employee.update、hr.employee.export、payroll.payslip.read、system.role.assign。
[Heading 2] 4.2 五类权限及生效位置

===== TABLE 4 (6x4) =====
层级 | 例子 | 前端职责 | 后端强制职责
菜单 | 可见“薪资管理” | 过滤左侧菜单树 | 返回菜单前确认授权；接口另行授权
页面 | 可访问 /hr/employees | 路由守卫，直接地址拦截 | hr.employee.read 校验
按钮/操作 | 新建、编辑、删除、导出、审批、发工资 | 按权限控制显示/禁用 | 每一写操作或导出接口重新检查
数据范围 | 仅本部门、本人、指定部门 | 用于提示当前视图范围 | 服务端 Query Scope、详情归属校验、批量写入逐项校验
字段 | 工资、证件号、银行卡、联系电话 | 脱敏展示 | API 序列化、筛选/排序/导出/附件下载均验证
===== END TABLE =====

[Body Text] 禁止用前端隐藏代替权限控制。 任何通过 curl、浏览器开发者工具、直接输入 URL 访问的未经授权请求，都必须被服务端拒绝。
[Heading 2] 4.3 权限资源编码和模型
[First Paragraph] 建议 permissions 统一表：id, code, name, resource_type(menu/page/action/api), parent_id, route_name, route_path, component_key, icon, sort, visible, status, risk_level。
[Body Text] 示例：
[Source Code] {
  "code": "hr.employee.export",
  "name": "导出员工档案",
  "resource_type": "action",
  "parent_code": "hr.employee.read",
  "risk_level": "high",
  "status": "enabled"
}
[First Paragraph] 前端权限标识与后端权限标识同源；菜单目录的显示可以随子页面授权自然展开，但父菜单授权不等于自动授权子页面或按钮。默认不使用模糊通配符；超级管理员特权在服务端受控处理，且不得越过公司/租户隔离和强制安全策略。
[Heading 2] 4.4 用户、角色与授权规则
[Compact] 一个用户多个角色。 允许“部门经理 + 考勤审批人”，角色可按公司绑定并可设置有效期。
[Compact] 一个角色多个权限。 权限应按页面、按钮、API 一一对应，不能将“可编辑”自动推断为“可导出”。
[Compact] 权限与数据范围成对授权。 role_grants 保存 (role_id, permission_id, data_scope_id, condition_json)，不能把角色 A 的“查看工资”动作与角色 B 的“全公司员工范围”拼成新的隐式越权授权。
[Compact] 多角色求值。 对同一操作，找到每个拥有该操作的有效 grant，分别计算其允许的数据集合，最后求并集；敏感字段还必须额外通过字段权限校验；强制禁用状态优先。
[Compact] 组织边界优先。 company_id 是强制前置过滤，不因角色并集而跨公司访问。
[Compact] 本人权限独立。 通过当前登录用户安全映射的 employee_id 判断 SELF，不信任前端传入的本人 ID。
[Compact] 权限立即失效。 更新用户角色/授权后递增 auth_version，刷新缓存并使老版权限上下文在下次请求时失效；重要撤权必须立即阻止 API 访问。
[Compact] 高危操作二次确认。 授权系统管理、工资导出、工资批次发布、大批量导出等要求强认证或复核；授予本人高危权限必须采用独立审批/双人控制。
[Compact] 超级管理员保护。 仅通过受控初始化创建，至少保留一个应急管理账户，禁止随意删除或从自身剥离最后的救援权限。
[Compact] 未列出的动作默认拒绝。 不默认给新菜单开放权限，不允许未知资源被自动允许。
[Heading 2] 4.5 数据范围枚举

===== TABLE 5 (8x3) =====
范围代码 | 含义 | 注意
SELF | 仅本人 | 依赖 user.employee_id
DEPT | 当前负责或所属部门 | 经理使用“负责部门”定义，普通员工使用“所在部门”定义
DEPT_TREE | 已授权部门与其有效下级部门 | 部门树以查询时点/业务时点核算
DEPT_SET | 特定部门集合 | 由管理员勾选部门 ID
COMPANY | 本公司全部 | 不等于跨集团全部
CUSTOM | 特定员工/项目/其他业务条件 | 必须白名单条件模板，不允许任意 SQL
NONE | 不允许访问任何业务数据 | 默认值
===== END TABLE =====

[Body Text] 读写双重校验： 列表的 WHERE 条件、单条详情、更新、删除、导出、报表聚合、附件下载都必须执行相应范围约束；修改部门/公司归属的操作还要检查“变更前对象可管理”与“变更后目标范围可操作”。
[Body Text] 历史口径： 员工调部门后，“当前员工列表”按当前部门过滤，“历史考勤、工资和部门编制报表”按记录保存的 department_id_snapshot 与业务日期归属过滤，避免历史统计随今天调岗而漂移。跨公司调动应以旧公司历史记录不可被新公司默认读取为原则。
[Heading 2] 4.6 字段级权限与数据脱敏

===== TABLE 6 (8x3) =====
字段类别 | 默认策略 | 有权使用时
姓名、工号、部门、岗位 | 按员工数据范围展示 | 正常返回
手机号、邮箱、地址 | 依业务必要性按角色遮罩或限量显示 | 记录读取与导出审计
身份证/护照号 | 默认部分遮罩，非必要不查询原文 | 受授权解密、限业务场景与访问留痕

[Body Text] 特别注意： 隐藏字段不能只发生在浏览器。分页 API、详情 API、搜索建议、导出 CSV/XLSX、报表聚合、文件元数据、错误信息和审计日志都要遵守字段规则；禁止通过“用不可读字段做筛选或排序”间接推断敏感信息。
[Heading 2] 4.7 推荐的权限配置界面
[First Paragraph] 系统管理 → 角色管理 → 新建/编辑角色：
[Compact] 基本信息：角色名称、编码、说明、适用公司、生效状态、有效期。
[Compact] 菜单与页面权限：左侧树选择业务菜单，父子节点分别控制；展示“已选页面 x 个”。
[Compact] 操作按钮权限：选中页面后列出“查看 / 新建 / 编辑 / 删除 / 审批 / 导入 / 导出”等原子能力；默认不全选。
[Compact] 数据权限：按每组动作选择本人、本部门、本部门及下级、指定部门、本公司、自定义；指定部门提供部门树多选。
[Compact] 敏感字段权限：身份证、银行卡、薪资、联系方式等单独配置“隐藏/脱敏/明文/允许导出”。
[Compact] 用户分配：选择账号、适用公司、授权开始与结束日期。
[Compact] 权限预览：选择某个用户，显示有效角色、可见页面、操作能力、具体数据范围与字段级结果；支持“模拟访问指定员工”。
[Compact] 变更提交：展示差异预览、高危授权二次审核、操作人/时间/审批单号。

[Heading 1] 05. 核心业务流程与状态机
[Heading 2] 5.1 员工入职闭环
[Source Code] 招聘候选人/手工入职登记
  -> 录入基础信息与入职资料
  -> 入职审批（可配置）
  -> 审批通过后创建/激活 employee 与 employment 记录
  -> 分配部门、岗位、负责人、工号
  -> 按策略创建并绑定系统账号（可选）
  -> 创建入职任务清单 / 合同待签 / 试用期提醒
  -> 仪表盘及报表更新
[First Paragraph] 规则：同一身份不应重复建档；招聘候选人转员工要经过数据核对；审批失败不得提前正式入职；入职日期、状态及部门有效期需要统一时点处理。
[Heading 2] 5.2 转正、调岗、调部门、调薪
[Compact] 由 HR 或有权限经理发起 employee_changes 异动申请，记录旧值、目标值、生效日、原因、附件。
[Compact] 提交审批后进入 PENDING，完成审批生成不可变履历，按照 effective_at 生效。
[Compact] 对未来生效异动可由计划任务执行；执行必须幂等。
[Compact] 调部门后更新组织归属、直属上级与动态数据权限所用的部门关系；原审批单和历史工资归属保持旧快照。
[Compact] 调薪改的是新生效期的薪资方案，不回写历史已确认工资批次。
[Heading 2] 5.3 离职闭环
[First Paragraph] 申请 → 审批 → 交接任务（物品、账号、合同、薪资、考勤）→ 确认离职 → 解除/冻结账号 → 撤销在职授权与通知 → 档案按规则保留。离职不是删除员工资料。冻结账号和敏感权限撤销需要有明确时效约束，避免离职后继续访问。
[Heading 2] 5.4 假勤审批闭环
[Source Code] 草稿 DRAFT
 -> 已提交 SUBMITTED
 -> 审批中 IN_REVIEW
 -> 通过 APPROVED / 驳回 REJECTED
 -> 已撤销 CANCELLED（依规则）
 -> 已结算 SETTLED（考勤/工资侧）
[First Paragraph] 假期余额使用 leave_ledger 记账（获得、占用、扣减、退还、调整），不是只维护一个可直接修改的“剩余天数”。请假、加班、出差要检查日期冲突、排班/节假日、撤销后的结算逆向调整；已结算记录不能直接改写，应走冲正或更正流程。
[Heading 2] 5.5 工资闭环
[First Paragraph] 薪资规则配置 → 锁定考勤/假勤输入快照 → 创建计薪批次 → 计算并留痕规则版本 → 薪资专员复核 → 授权审批 → 发布工资条 → 发放确认 → 批次封存。批次发布后应不可任意重算；如需修改，产生更正批次/冲正记录。工资项、个税及社保口径由公司实际所在地、有效政策和已批准方案配置，不在代码中固化未经核对的法定费率。
[Heading 2] 5.6 通用审批引擎
[First Paragraph] V1.0 采用数据库驱动的有限状态机和可配置节点规则，不引入重量级 BPMN 引擎；可支持：
[Compact] 模板：类型、版本、启用期、公司、条件规则、节点顺序。
[Compact] 节点：指定用户、直属上级、部门负责人、角色用户、多人会签/或签。
[Compact] 动作：提交、撤回、同意、驳回、转交（若流程允许）、抄送。
[Compact] 操作合法性：审批人必须是当前活动节点候选，不能自我冒充或跳节点。
[Compact] 流程实例应固定模板版本及节点快照；修改模板不影响历史单。
[Compact] 支持节点超时提醒、代理审批设置、幂等与完整审批轨迹。
[Compact] 审批通过后的“业务生效”通过 Outbox + 队列实现，失败可重试，不允许重复扣假/重复建档。

[Heading 2] 7.1 数据设计通则
[Compact] 主键优先 BIGINT/有序唯一 ID；业务编号独立唯一索引（按 company_id 约束）。

[Heading 1] 08. API 设计与权限校验契约
[Heading 2] 8.1 通用约定
[Compact] API 路径：/api/v1/...；JSON UTF-8；日期 ISO 8601；金额以字符串 Decimal 传输。
[Compact] 响应：{ "code": "OK", "message": "success", "data": {}, "request_id": "..." }；列表包含 items, page, page_size, total。
[Compact] 失败使用 HTTP 401（未认证）、403（无权限）、404（不可发现资源）、409（冲突）、422（校验失败）、429（限流）；不得全部返回 HTTP 200。
[Compact] 更新接口使用乐观锁版本号或 updated_at 条件，避免多人覆盖。
[Compact] 创建/提交/审批/工资发布等关键命令支持幂等键 Idempotency-Key。
[Compact] 所有下载、批量导入/导出采用后端任务+结果查询+短期签名下载，需二次授权。
[Compact] OpenAPI 为接口契约唯一事实源，前端类型尽可能由其生成。

[Heading 2] 10.2 导入要求
[First Paragraph] 模板版本化 → 下载模板 → 文件上传至私有临时区 → 异步预检（格式、必填、唯一性、部门岗位映射、字段许可）→ 展示错误行 → 用户确认 → 事务分批导入 → 结果报告与审计。禁止导入覆盖未获权限的部门员工，禁止“存在则默认覆盖”未告知用户。
[Heading 2] 10.3 导出要求
[First Paragraph] 仅对授权查询快照执行导出；服务端字段白名单、文件水印/审计字段（如适用）、导出任务过期控制、短效下载地址；敏感字段明文导出需独立授权。分页接口不能“只过滤当前页”导致总数、搜索结果或 Excel 泄露。
[Heading 2] 10.4 搜索要求
[Compact] 组织、姓名、工号、合同、招聘状态等可筛选；手机号/身份证等只能按明确权限支持适度查询，避免枚举。
[Compact] 搜索请求使用白名单字段及安全参数绑定；后端统一数据范围过滤；限制 page_size。
[Compact] 模糊搜索对敏感信息实施频率限制、最低必要长度和审计；普通员工不能通过枚举工号发现其他员工。
[Heading 1] 11. 安全、隐私及合规
[Heading 2] 11.1 安全基线
[Compact] HTTPS、HSTS、合理 CSP、Cookie 安全属性、CSRF/XSS/SQL 注入防护；使用参数化查询与严格输入验证。
[Compact] 密码使用现代强哈希算法；登录限流、异常登录提醒、会话管理、MFA（高权限账号强制）。
[Compact] 默认拒绝 + 每请求授权 + 资源归属核验（尤其 /employees/{id}、下载、导出）。
[Compact] 高危动作双人复核/强确认；不得允许审核人审批自己的工资批次或权限升级（按职责分离规则）。
[Compact] 薪资、证件号、银行账号加密存储；脱敏返回；密钥独立管理与轮换。
[Compact] 私有附件访问通过鉴权下载；病毒扫描、后缀/MIME 校验和最大文件限制；禁止可执行文件直接公开访问。
[Compact] 审计保留账号、请求 ID、动作、业务对象、字段名称、变化摘要、成功失败、时间/IP（合法必要范围）；不要记录密码、令牌和敏感明文。
[Compact] 数据库最小账户权限；备份加密和恢复演练；环境变量和 Secret 管理；生产禁止调试端点与演示账号。
[Compact] 员工离职、调部门、撤权、密码重置都要确保缓存或会话立即失效。
[Compact] 安全测试应覆盖 IDOR/水平越权、垂直提权、批量越权、恶意导入、任意文件下载、敏感字段旁路、并发双审批。
[Heading 2] 11.2 中国境内部署的个人信息保护注意事项
[First Paragraph] 《中华人民共和国个人信息保护法》对个人信息处理的合法性、必要性、告知、敏感个人信息、权限控制等提出要求。人力资源管理所必需的处理可能具有相应法定处理基础，但不能据此认为所有敏感信息均可无限采集、无限查看或任意跨境传输。应基于真实业务、依法制定的劳动规章制度、适用法规和公司管理要求，对字段、告知、留存、访问、共享、删除及跨境作合规评估。
[Compact] 采集前建立“字段—使用目的—处理基础—可访问角色—保留期”清单。
[Compact] 具备必要个人信息处理告知；对敏感个人信息按照适用法律实施特别保护，评估单独同意等要求是否适用。
[Compact] 实施个人信息查询、更正与权限申诉机制；离职档案留存须有法定/业务必要性依据与删除流程。
[Compact] 薪酬、身份、健康等敏感信息的导出、对外共享、备份与跨境接入需专项评估。
[Compact] 本实施书仅为工程合规基线，不替代公司法务根据实际地区、用工及数据流的专业审查。

IAM-08 | 用户同时具有多个角色 | 仅对同一操作在各自 scope 内并集，不跨角色拼接高权限
IAM-09 | 管理员撤销角色后旧标签页继续调用 API | 立即拒绝，缓存及授权版本正确更新
IAM-10 | 角色只配置菜单、不配置“导出” | 页面可看（若有查看权限），导出按钮不显示且 API 403
IAM-11 | 切换公司后沿用旧公司记录 ID | 旧公司接口不可访问
IAM-12 | 普通员工批量请求他人工资条 | 全部拒绝，不能通过批量接口越权
IAM-13 | 用户试图给自己分配超级管理员权限 | 被审批/职责分离策略拦截
IAM-14 | 历史导出任务链接被转发给无权用户 | 无有效授权不能下载
===== END TABLE =====
