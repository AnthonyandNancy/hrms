# HRMS V1.1 生产完整性审计（2026-11-25）

> 审计对象：`HRMS-V1.1实施书.md`（V1.1 主需求）＋ `docs/HRMS_V1.0_解决方案_第一性原理重构.md` / `docs/HRMS_V1.0_实施计划_30周路线图.md`（V1.0 辅助）＋ 当前 `main` 代码与生产式 Compose 栈。
> 审计性质：只读证据审计。除本文与后续方案/计划文档外，未修改业务代码、迁移或 OpenAPI。
> 审计基线：`main @ bdd20da`；生产式栈 `factoryhr-*`，真实 Laravel + MySQL，登录账号为安装器创建的 `installer`。

## 1. 结论先行

这不是“补几个页面”的问题。当前系统是**V1.0 架构骨架 + 少量纵切**，而 V1.1 要求的是**17 个截图菜单、140 个子页面、14 个平台模块、26 个工作包**的生产可用系统。差距同时存在于五个层面：

1. **需求层**：V1.1 文档内部存在权限命名、API 前缀、实体命名、公司/租户边界、数据范围枚举、系统管理员是否可读工资等未归一化的冲突；照字面直接编码会得到互相冲突的系统。
2. **授权生命周期层**：`auth_version` 同时承担“会话失效版本”和“授权绑定版本”，密码变更后绑定不随版本迁移，导致超管合法改密后所有能力静默归零。
3. **身份模型层**：系统管理员可以没有 `employment`，但考勤、假期、工资条等 SELF 控制器把 `employmentId` 默认成 `0` 或直接 404，管理员因此无法使用任何员工自助页面。
4. **契约层**：前端大量使用 `as never` 与手写类型，OpenAPI 生成脚本只生成空壳；真实后端返回 snake_case/分页对象/缺失字段，而视图按 camelCase 数组渲染，工资条页 100% 进入全局错误边界。
5. **交付层**：前端只有 20 条路由记录、18 个视图、12 个导航项；V1.1 的 140 个页面中约 123 个完全缺失、其余多为单页薄实现。测试全绿只证明 mock 形状与纯函数正确，不能证明真实栈可用。

**本质原因**：项目把“文档覆盖”误当成“系统完成”，把“mock 通过”误当成“生产可用”，并把授权、身份、契约、页面四个不同维度混在同一套快速验收里。V1.1 必须按**真相源优先（source of truth first）**重做交付顺序：先把契约、授权生命周期、身份边界和页面注册表建成不可绕过的骨架，再按主链路逐域补齐，而不是继续堆页面。

## 2. 本次实际复现的证据

### 2.1 超管合法改密后能力归零（P0）

- 安装器创建 `installer`，角色 `SYSTEM_ADMIN`，`authority_bindings` 中为 `*` + `LEGAL_ENTITY` + `P3_RESTRICTED`，写入时 `auth_version=2`。
- 通过真实 `POST /v1/auth/password` 改密成功后，用户 `auth_version` 升为 4，但既有绑定仍为 2，`GET /v1/me/capabilities` 返回 `capabilities: []`、`wildcard: false`。
- 重新登录成功（200），但侧栏只剩“我的工作台”；工资批次、公告、仪表盘 API 返回 403。
- 代码证据：`AuthController::changePassword()` 提升 `auth_version` 并吊销会话；`BindRoleCommand` 的“已绑定则跳过”只看 `valid_to`，不迁移绑定版本；`EloquentAuthorityBindingRepository` 按 `auth_version` 精确匹配。
- **影响链**：合法安全操作 → 授权静默失效 → 超管无法治理 → 只能手工改库 → 生产不可维护。

### 2.2 系统管理员不是员工，SELF 页面必然 404（P0）

- 安装器只创建管理员账号，不创建 employment；`employment_user_links` 为空。
- `AttendanceController::month()` 调用 `scope->employment($actor, (int)($actor->employmentId ?? 0), ...)`，`LeaveController::balances()` 同样默认 `0`，`TimeRequestScope::employment()` 在无任职时抛 `NotFoundOrForbiddenException`。
- 真实栈验证：`installer` 登录后 `/v1/time/attendance?month=2026-11`、`/v1/time/leave/balances`、`/v1/time/leave/requests`、`/v1/time/leave/ledger` 全部 404；前端“假期与余额”“考勤日历”显示加载失败。
- **影响链**：管理员无法自测/配置与“人”绑定的功能；员工自助页面对新管理员永久不可用；排障被误判为权限 bug。

### 2.3 工资条契约失配导致整页白屏（P0）

- 后端 `GET /v1/payroll/payslips` 返回 `{items,page,page_size,total}`，条目为 snake_case（`gross_cents`/`net_cents` 等），不返回 `employeeName/period/payDate/state` 等视图字段。
- 前端 `frontend/src/api/http.ts` 的 `listPayslips` 为 `unwrap(client.get('/payroll/payslips')) as never`，视图 `PayslipsView.vue` 直接按数组遍历并将 `undefined` 传给 `MoneyText` → `formatMoney()` 抛 `TypeError: Money must be an integer number of cents`。
- 真实栈浏览器验证：`/payroll/my-payslips` 显示“页面暂时无法渲染”，`App.vue` 的全局 `onErrorCaptured` 替换整个 `<RouterView>`。
- **二阶影响**：一个字段缺失会清空导航、未保存输入和整个工作区；后续任何路由仍停留在错误页，直到硬刷新。
- **三阶影响**：用户不再信任“页面失败是局部问题”，改用截图/Excel 线下流程；系统审计与数据回流断裂。

### 2.4 页面覆盖严重不足（P0）

- V1.1：17 个菜单、140 个业务页、14 个平台模块、6 个基础页（共 160 条注册表）、26 个工作包。
- 当前：`frontend/src/router/index.ts` 20 条路由记录（含 login/forbidden/not-found），18 个视图组件，12 个导航项；按路径匹配，V1.1 的 140 个页面中 **123 个完全缺失、17 个仅部分实现**。
- 完全缺失的代表：岗位管理、员工异动、劳动合同、加班管理、出差管理、绩效考核、招聘需求、候选人、培训管理、社保福利、工作日历、字典参数、消息中心、系统管理（用户/角色/菜单/权限/数据范围/字段策略）、员工自助门户、报表订阅/构建器等。
- 部分实现：仪表盘只有单页，无部门/人员/异动/招聘子页；员工只有目录，无建档/详情/教育/履历/证照/附件/导入；审批仅有列表+详情抽屉，无流程配置/已办/抄送/催办；薪资只有批次与工资条，无薪资项/方案/员工薪资档案/社保/输入快照/发放/冲正/报表。

### 2.5 API 契约与生成链失效（P1）

- `frontend/scripts/generate-api.mjs` 不调用已安装的 `openapi-typescript`，固定写出 `paths = Record<string, never>`；`src/generated/api.ts` 不存在。
- `frontend/src/api/contracts.ts` 是手写镜像；全前端约 **30 处 `as never`**、44 处裸 adapter 调用，`unwrap()` 不校验 envelope 与 data。
- OpenAPI 测试只断言“路由路径已登记”，不校验请求/响应 schema；真实漂移只能靠运行时崩溃暴露。
- 已确认的额外真实失配：
  - 管理端 `roles` 后端返回 `{roles:[...]}`，前端按数组处理；`memberCount/riskLevel/owner` 被客户端捏造。
  - `/access-review` 后端只有 `scheduled/unused/sod_risks`，前端却合成姓名、角色、到期日、状态。
  - `/users/{id}/bindings` 后端要求 `capability_code/anchor_type/anchor_id/field_profile/purpose_code`，前端发送 `capabilityCode/anchorName/fieldProfiles` 且默认 `userId=0`。
  - 导出下载后端要求 `?token=`，前端不带 token，真实环境必然 404。
  - 案例详情/决定/重试、假期列表/账本、考勤月视图、指标下钻等均存在字段或包裹形状差异。

### 2.6 测试的“绿色”与生产可用脱节（P1）

- 后端 818 tests / 37,064 assertions 全绿；前端 52 unit tests 全绿。
- 但真实后端 E2E 默认因缺少 `HRMS_DEMO_PASSWORD` 整组 skip；发布脚本 `verify_release.sh` 只跑 mock E2E，不跑真实栈。
- Mock adapter 的工资条/管理/导出形状与真实后端不同；mock E2E 的工资条和导出旅程无法发现真实缺陷。
- 没有组件级测试用真实 payload 挂载 `PayslipsView`、`PayslipDetailView`、`AdminView`、`LeaveView`、`AttendanceView`、`CaseDetailView`、`ReportsView`。
- 没有运行时路由覆盖审计；删除/改名页面后现有测试仍全绿。
- 证据文件与当前工作树不一致：`docs/12-plan-completion-inventory.md` 基线为 `998649f`，当前 `bdd20da`；证据日志包含不同 bundle hash 和 `.worktrees/superuser-baseline` 路径。

### 2.7 生产交付与可追溯性缺口（P1）

- 镜像固定为 `:local`，staging 部署脚本远端 `docker compose pull` 无法拉取本次构建；构建无 commit SHA/build time 标签。
- `/v1/health`、`/v1/meta` 只报静态 `1.0.0`，无法判断 SPA/API 是否同源同版本。
- 部署 smoke 只检查 API，不检查 `/`、SPA 路由、hashed asset。
- MinIO/基础镜像使用可变 tag，构建不可复现。
- `VITE_API_MODE` 保护只在 Vite 配置层，镜像构建后无 bundle 断言。

## 4. 根因分析（第一性原理）

### 4.1 直接原因与本质原因分开

| 层级 | 直接原因 | 更本质的原因 |
|---|---|---|
| 工资条白屏 | 前端把分页对象当数组、字段未映射 | **契约不是事实源**：手写类型 + `as never` + 无响应校验，使编译期无法发现漂移 |
| 超管 403 | 改密提升 `auth_version`，绑定未迁移 | **一个版本号承担两种语义**：会话撤销与授权快照被混为一谈；授权更新不是原子“重发当前有效绑定” |
| 假期/考勤 404 | 管理员无 employment，控制器默认 0 | **User 与 Employment 边界错误**：账号身份被当成员工身份；SELF 能力被视为所有账号的默认能力 |
| 页面大面积缺失 | 只做了少量纵切 | **以“文档章节覆盖”替代“页面/接口/权限/测试四件套覆盖”**；没有可执行的覆盖矩阵与发布门禁 |
| 测试全绿但不可用 | mock 与真实形状不同，真实 E2E 被 skip | **验证对象错误**：验证了前端与 mock 的一致性，而非前端与真实后端的契约 |
| 同类问题反复出现 | 每次修一个页面/字段 | **缺少跨模块不变量**：契约、授权版本、身份边界、错误边界、页面注册表都没有单一权威实现 |

### 4.2 五个不可再分的不变量

1. **单一契约事实源**：OpenAPI 定义请求/响应；前端类型由它生成；运行时对关键响应做 schema 校验；任何 adapter 不得用 `as never` 绕过。
2. **授权版本可重放**：`auth_version` 只表示“当前有效授权快照的世代”。任何改变授权的操作必须在同一事务内**重写/迁移全部当前有效绑定到新版本**；仅改密码/会话撤销不得改变授权语义。
3. **身份边界显式**：`User` 是账号，`Employment` 是雇佣关系；SELF 能力只在存在有效任职时可用；系统管理员的能力是“治理能力”，不是“员工自助能力”的替代。
4. **错误隔离**：路由级错误边界 + 页面级 ErrorState + 全局兜底三层；单个组件异常不得清空 shell；同一错误只呈现一次，并带 `request_id`。
5. **覆盖可执行**：页面注册表 = 菜单 + 路由 + 组件 + 权限 + API + E2E + 空/错/无权限态；CI 对比 V1.1 清单，缺一即失败。

### 4.3 跨领域参照

| 领域 | 借鉴机制 | 对本项目的落点 |
|---|---|---|
| 数据库迁移 | schema version + forward-only migration | 授权绑定按版本重放；页面/契约也应有可核对的“版本” |
| 编译器 | 类型检查在运行前失败 | OpenAPI 生成类型 + 运行时 schema 校验，禁止 `as never` |
| 航空/医疗 | checklist + sterile cockpit | 每个页面交付四件套清单；发布前真实栈巡检 |
| SRE | error budget + golden signals | 以真实 E2E 通过率、契约漂移数、403/404 率作为发布门禁 |
| 财务 | 双人复核、不可变账本 | 授权变更、工资发布、导出走 SoD 与不可变审计 |
| 供应链 | SBOM + digest pinning | 镜像带 commit SHA、digest；部署 smoke 校验 SPA/API 同版本 |
| 操作系统 | 能力目录 + 显式授权 | 能力目录代码化、锚点编译谓词；管理员选择全权时，审计与 SoD 是补偿控制 |

## 5. 二阶与三阶影响推演

### 5.1 若只修截图里的工资条

- 直接效果：工资条页可打开。
- 二阶：同一类 adapter 漂移仍在假期、考勤、审批、报表、管理端；用户继续遇到白屏/空数据。
- 三阶：团队形成“报错→补字段”的救火模式；每次后端改字段都可能引入新白屏；测试仍无法提前发现。
- 结论：**不可接受**。必须同时建立契约事实源
## 6. 建议的目标架构（生产基线）

### 6.1 分层

```text
SPA: 受控路由注册表 + 页面四件套 + 三层错误边界
  - menu tree from /me/permissions (server)
  - route table is a code-owned registry
  - generated API types + runtime schema validation
API: OpenAPI 3.1 单一契约 + capability middleware
  - every route: auth.session + csrf.header + capability
  - every response: typed schema + request_id
Domain: Person-Employment-Assignment + Case/Decision/Effect
  - one writer per table; contracts between modules
  - append-only ledgers; immutable published payroll
Identity/Authority: User != Employment
  - auth_version = authorization snapshot generation
  - binding replay inside the same transaction
  - wildcard grants every capability (including P3); superuser may read payroll
Platform: audit/outbox/idempotency/files/retention
  - append-only audit; redaction; retention legal hold
```

### 6.2 关键决策（建议）

- **D1｜契约事实源**：OpenAPI 3.1 是唯一契约；`openapi-typescript` 生成类型；CI 运行 `openapi:check`；adapter 不得 `as never`；关键响应用 Zod 做运行时校验。
- **D2｜授权版本重放**：`auth_version` 变更必须在一个事务内把当前有效绑定复制/迁移到新版本；改密只吊销会话，不改变授权快照；新增 `authorization_revision` 或在绑定表上实现“版本迁移”命令，并用测试锁死。
- **D3｜身份边界**：`User` 与 `Employment` 解耦；SELF 控制器必须先解析有效任职，不存在时返回明确的 409/422 业务错误（如 `NO_ACTIVE_EMPLOYMENT`），而不是 404；管理员访问自助页显示“当前账号未绑定员工”而不是白屏。
- **D4｜管理员全权**：`*` 展开全部能力（含 P3 工资）；管理员可读工资；P3 读取/导出写不可变审计；SoD 风险提示但不阻断管理员。
- **D5｜三层错误隔离**：App 级只做最后兜底；AppShell 级捕获路由错误并保留导航；页面级 ErrorState 带 `request_id`；同一错误去重；路由切换自动清除边界错误。
- **D6｜页面注册表**：`frontend/src/router/registry.ts` 用类型化对象声明每个页面的 `path/name/component/capability/menu/group/requiredApis/emptyState/errorState/e2e`；CI 与 V1.1 清单 diff。
- **D7｜真实栈门禁**：Compose 起 MySQL/Redis/MinIO/PHP/nginx，执行安装器、创建合成租户、跑真实 E2E；mock E2E 只做快速反馈。
- **D8｜可追溯发布**：镜像 tag 含 git SHA；`/v1/meta` 返回 commit/build time；SPA 注入 `VITE_BUILD_SHA`；部署 smoke 检查 `/`、SPA 路由、hashed asset、`/v1/health`、`/v1/meta`。
- **D9｜统一权限词汇**：确定一套能力码（建议保留现有 `people.employee.read` 等作为执行码），在 UI/菜单层建立“资源-动作”映射；V1.1 的 `employees:view` 仅作为兼容别名，不进入后端授权。
- **D10｜审计与 SoD**：授权变更、敏感字段读取、导出、工资发布、离职工资结算必须写不可变审计；高危操作必须 step-up + 双人/独立审批。

## 7. 方案备选与取舍

| 方案 | 内容 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A. 继续补页面 | 按截图逐页加 Vue 文件 | 快出观感 | 契约/授权/身份仍错；返工巨大 | 否 |
| B. 先修内核再补页面 | 契约+授权+身份+错误边界+注册表，然后按主链路交付 | 一次修复系统性缺陷；可增量上线 | 前期看不到大量页面 | **推荐** |
| C. 完全按 V1.1 重写 | 新建 sys_* 表、/system/*、RBAC+DataScope | 贴近文档字面 | 丢掉已实现的账本/时间/审批内核；迁移风险极高 | 否 |
| D. 保留 V1.0 内核，V1.1 作为产品层 | 领域内核不变，补页面/API/权限映射 | 风险最低；可复用 818 测试 | 需裁决文档冲突与词汇 | **推荐（与 B 组合）** |

**推荐组合：B + D**——保留 V1.0 的时间化事实、账本、Case-Decision-Effect、能力锚点内核；把 V1.1 当作产品层与页面层需求，通过契约、注册表、权限映射、真实栈门禁落地。

## 9. 验收标准（生产口径）

### 9.1 每个页面（四件套）

- 路由/菜单：注册表中有且仅有一处声明；权限码与后端同源。
- API：OpenAPI 有请求/响应 schema；真实后端返回通过运行时校验。
- 权限：至少 4 类负测（未登录/无能力/越锚点/越字段或导出）。
- UI：加载、空、错误、无权限、数据不完整五态；危险操作二次确认。
- 测试：组件测试用真实 payload；真实栈 E2E 至少一条快乐路径 + 一条拒绝路径。
- 审计：敏感读取/导出/状态变更留痕，可按 `request_id` 追踪。

### 9.2 系统级

- `auth_version` 不变量测试：改密/撤权/角色变更/MFA/离职后能力与绑定一致。
- 登录→12 条现有路由→160 条注册表巡检 0 错误边界、0 非预期 403/404。
- OpenAPI 契约测试：所有路由 schema 与实现一致；无 `as never`。
- 真实 Compose E2E：安装器→登录→主链路→导出→审计→回滚。
- 构建可追溯：镜像 digest/SHA、`/v1/meta`、SPA build SHA 三者一致。
- 性能：300 并发 P95<500ms（服务端）；混沌 ≥12 场景；备份恢复 RTO/RPO 达标。

## 10. 风险与缓解

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| V1.1 文档冲突导致返工 | 高 | 高 | Phase 0 先裁决 C1-C8，写 ADR；冻结词汇/路由/实体映射 |
| 160 条页面一次性交付失控 | 高 | 高 | 按主链路分波；每波可独立上线；页面注册表驱动 |
