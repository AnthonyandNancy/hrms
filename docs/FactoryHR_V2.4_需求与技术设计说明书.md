# 第一部分 需求拆解与需求摘要

## 1. 需求名称

**FactoryHR V2.4 薪酬规则引擎与 21 模块业务闭环整改及全管理后台人工验收需求**

## 2. 背景

### 2.1 版本演进

| 版本 | 主要结论 | 对本需求的意义 |
|---|---|---|
| V2.0 | 完成架构根因审计和 160 路由盘点，识别页面职责混乱、权限动作不完整、员工建档非原子、技术文案泄漏、单公司与租户模型冲突等问题 | 确定本次整改不是页面美化，而是业务、数据、权限和交付方式整改 |
| V2.1 | 完成全量整改设计，明确单公司、内网、账号密码登录和角色/菜单/页面/按钮/数据/字段权限 | 作为不可偏离的产品边界 |
| V2.2 | 工作区无独立交付包；V2.3 引用了其 155 路由矩阵结论 | 以 V2.3 对 V2.2 的继承结论作为旧能力盘点依据 |
| V2.3 | 将旧入口归并为 21 个业务模块，形成 155 个历史页面/入口、458 张功能级核对卡、12 条跨模块 E2E | 作为模块、页面和功能点盘点基线 |
| V2.4 | 深化 M13 薪酬规则、员工—合同—薪酬关系、计薪事实、快照、更正、Element Plus 交互和干净部署，补充 T01–T24 验收矩阵 | 作为最新权威增量；与 V2.3 未冲突内容共同生效 |

### 2.2 当前存在的问题

- 页面、路由、按钮和接口数量不能证明管理后台业务闭环已经可用。
- 薪酬配置、员工档案、合同约定、假勤事实、福利、绩效和工资结果尚未形成统一、可追溯的计薪链。
- 工资存在 `employment_terms` 与 `employee_compensations` 双事实源，调薪和合同关联不能可靠进入实际计算。
- 考勤、请假、加班和出差审批与后续业务效果不一致；缺失考勤可能被当作全 0，进而按满勤计薪。
- 批次、输入快照、复核、审批、发放、工资条发布和更正的状态边界需要统一。
- 权限、数据范围、字段权限和导出权限需要服务端统一执行，不能只靠隐藏按钮。
- 绩效、福利、Offer 薪资和培训结果未形成进入薪酬的受控链路。
- 页面仍存在英文枚举、技术编号、接口说明、原生控件、金额浮点展示和缺失状态处理。
- 生产初始化、默认演示数据、升级、重复安装和权限目录同步路径不安全。
- 尚未完成覆盖全部管理后台功能点的 Playwright MCP 人工浏览器验收。

### 2.3 期望改善结果

- 管理后台从“有页面、有接口”变为“每个模块的真实用户任务可以完成并留下可信结果”。
- 21 个模块具备真实业务闭环，关键上下游可以追溯。
- 薪酬规则、有效期、输入快照、审批、发放、工资条和更正形成唯一、可重放的业务链。
- 所有业务页面具备中文、统一交互、真实数据、权限控制、异常反馈和持久化结果。
- 通过 Playwright MCP 模拟真实人员，逐项验收管理后台全部功能点，并根据证据决定上线。

### 2.4 需求确定性

**已确认：**

- 按 21 个业务模块组织整改和验收。
- 以 V2.4 为最新裁决，V2.3 中未冲突内容继续有效。
- 单公司、内网、账号密码登录，不强制 MFA。
- 旧能力不能因为页面归并而静默消失。
- 功能验收必须使用 Playwright MCP 模拟人为操作，不得用机械自动化测试替代。
- 本需求不设置阻塞性待确认事项。

**合理推测：**

- V2.2 的独立材料未单独提供，其结论通过 V2.3 的 155 路由矩阵继承。
- 当前路由数、动作数和测试数只代表现状清单，不代表目标范围和完成度；执行时必须重新锁定实际 HEAD。
- V2.4 计算样例是验收测试数据，不是公司法定工资政策；实际参数由配置决定。

**待确认内容：**

- 无。

## 3. 目标

### 3.1 总体目标

将 FactoryHR 整改为单公司内网可生产使用的人事管理系统，完成人员、组织、合同、异动、考勤、请假、加班、出差、薪酬、福利、绩效、招聘、培训、审批、通知、报表、权限、审计和部署的模块化闭环。

### 3.2 可验收目标

1. 21 个业务模块全部完成真实读写、状态变化、权限控制和下游联动。
2. 155 个历史页面/入口和 458 张功能核对卡全部有“保留、迁移、合并、替代或明确非目标”的结论。
3. 当前管理后台所有页面、页签、按钮、表单、列表操作、状态转换和关键异常均可由真实角色在浏览器中完成。
4. 薪酬形成完整链路：员工与合同版本 → 执行薪酬版本 → 方案与规则 → 计薪事实 → 输入快照 → 计算 → 复核 → 批准 → 发放登记/工资条发布 → 更正 → 报表。
5. 至少通过 12 条跨模块业务闭环和 V2.4 T01–T24 验收矩阵。
6. 新数据库完成干净初始化；已有数据库升级不丢失员工、合同、薪酬版本、工资条、角色和审计记录。
7. 所有管理后台功能点形成 Playwright MCP 人工验收证据。
8. 上线时 P0/P1 阻断项为零、未授权金额泄漏为零、新库演示业务数据为零、工资对账差异为零或有正式批准解释。

## 4. 用户角色与场景

### 4.1 角色

| 角色 | 主要使用场景 | 典型操作 | 关键限制 |
|---|---|---|---|
| 系统超级管理员 | 初始化、权限、基础配置、运维审计 | 创建管理员、用户角色、菜单页面动作、公司资料、日历、字典、审计 | 不自动成为员工，不自动成为审批人，不绕过业务状态和审计 |
| HR 管理员/人事专员 | 员工全生命周期 | 建档、编辑、调动、转正、离职、合同登记、代申请、查询授权员工 | 未授权不能查看薪资、证件或其他敏感字段 |
| 考勤/假勤专员 | 排班、打卡、异常、请假、加班、出差、月结 | 处理补卡和异常、维护规则、管理余额、确认加班、月结 | 已锁定事实不能静默修改，不能修改工资条 |
| 薪酬专员 | 薪酬配置、调薪、核算准备 | 维护项目/方案、绑定合同与方案、发起调薪、准备批次、试算、更正 | 不自动拥有复核、批准、发放、发布或全部导出权限 |
| 复核/批准/发放人员 | 工资复核、批准、发放登记、发布 | 查看差异、退回、批准、登记发放、发布工资条 | 不能修改计算明细，批准与执行分离 |
| 部门经理 | 本人和授权部门业务、审批待办 | 查看授权部门员工、发起和审批授权业务 | 不因“经理”身份自动获得其他部门或工资金额权限 |
| 普通员工 | 本人工作台和员工自助 | 查看本人档案、合同摘要、考勤、工资条、培训绩效，发起本人申请 | 对象固定为本人，不能通过改地址或参数查看他人 |
| 招聘/培训/绩效专员 | 人才领域管理 | 招聘需求、候选人、面试、Offer、培训、绩效周期和结果 | 不能借用人才页面读取薪酬、账号或未授权员工数据 |
| 审计查看员 | 审计和权限变更检查 | 查询、筛选、查看脱敏差异和授权导出 | 只读，不能分配角色或修改业务 |

### 4.2 关键场景

1. **新环境初始化**：部署者创建唯一超级管理员，系统无演示业务数据；管理员配置公司、部门、岗位、角色和权限后创建首位员工。
2. **员工生命周期**：招聘录用或手工建档 → 合同登记 → 薪酬配置 → 账号绑定 → 转正、调岗、调薪、离职，均按生效日期和版本留痕。
3. **工资核算**：配置项目/方案 → 绑定员工合同及方案 → 归集假勤、福利、绩效和一次性奖扣 → 试算 → 复核 → 批准 → 发放登记 → 发布工资条。
4. **动态变更**：工资草稿期间假勤撤销、加班改调休、合同续签或调薪时，系统提示输入过期并重算；已冻结或已发放工资只走更正。
5. **员工自助**：员工只能查看本人已发布工资条、合同摘要、假勤、培训绩效；撤权后旧链接不可访问。
6. **权限验证**：管理员调整角色和字段权限后，菜单、按钮、数据范围和敏感字段立即按新权限表现。
7. **审计与报表**：敏感查看、导出、审批、薪资发布和更正均可追溯；汇总、明细和员工工资条金额一致。

- 形成 155 个历史入口的保留/迁移/合并/替代说明和 458 张功能卡覆盖表。
- 形成测试角色、测试数据、前置条件、证据要求和阻断项清单。
- 本阶段只定义业务差距、依赖、验收和交付顺序，不展开具体代码文件实施计划。

### 5.3 全管理后台人工验收

- 使用 Playwright MCP 浏览器工具，以真实角色登录真实前端和真实后端环境。
- 按功能点清单执行导航、查询、筛选、分页、表单、提交、取消、审批、刷新、重新登录和跨角色访问。
- 记录账户、路径、前置数据、操作步骤、实际结果、截图/快照和 `PASS / FAIL / BLOCKED`。
- 当前管理后台所有可操作功能点均须执行；状态转换、权限差异、空数据、错误、重复操作和关键边界均覆盖。
- 不得用机械自动化测试、接口调用记录、日志或代码审查替代人工浏览器验收。

## 6. 业务规则

### 6.1 单公司与身份

- 系统只有一个公司身份、一个公司时区和币种。
- 不存在租户、法人切换、多公司账套或跨公司数据。
- 登录账号与员工任职分离；管理员可以没有员工任职。
- 操作者、业务对象所属员工、审批人分别记录。
- 员工自助对象由当前账号绑定推导，不能由前端选择他人。

### 6.2 权限

- 页面进入权、动作权限、数据范围、字段可见性和导出权限分别判断。
- 列表、详情、选择器、报表、图表、导出、附件、通知链接和错误响应使用同一权限边界。
- 前端隐藏按钮不能替代服务端拒绝。
- 角色变更、账号停用或撤权后，已有会话、旧页签和旧链接不能继续使用旧权限。
- 超级管理员不能跳过薪资状态、审批分离、审计或数据完整性限制。

### 6.3 数据所有权

- 人员、任职、组织、岗位、合同、时间事实、薪酬执行配置、工资结果、绩效、招聘、培训、审批、权限和审计各有唯一主写入方。
- 下游只能读取授权事实、引用版本或调用受控业务动作，不能维护第二份主数据。
- 跨模块结果必须可追溯到源单据、版本、操作者和生效时间。
- 报表和看板只做只读投影，不能成为第二写入口。

### 6.4 时间与版本

- 业务日期按公司时区解释；存储和展示口径一致。
- 合同、任职、薪酬、方案、规则、福利和日历使用有效期版本；历史事实不可被新版本覆盖。
- 未来版本在生效日前不得提前应用。
- 同员工、同业务对象、同生效日不得存在冲突版本。
- 月中建档、调薪、调岗、入职和离职按有效区间分段；周期级税费、社保和一次性项目不得因分段重复执行。
- 已冻结工资输入和已发布结果必须保留当时版本。

### 6.5 薪酬

- 薪资项目、规则和方案必须经过草稿、校验、发布、使用和退役生命周期；已发布版本不能原地修改。
- 规则使用受控表达式和受控函数，不允许任意代码、脚本、系统时间或随机数参与工资计算。
- 必须验证未知变量、循环依赖、类型/单位不匹配、除零、溢出和缺少参数。
- 员工薪酬档案必须绑定同一员工的雇佣关系、有效合同版本、薪酬方案版本和生效期间。
- 同一批次可为不同员工使用不同方案，不允许批次级方案覆盖个人方案。
- 金额使用精确金额规则，保留舍入位置；页面以元展示时不得出现浮点误值。
- 缺失数据必须阻断、标记不适用或通过有记录的授权例外处理，不能默认为零。
- 已批准或已结清工资只能通过新批次更正；更正按“目标结果减去原结果及全部有效更正累计”的增量计算。
- 计税、社保标记和单位成本标记必须真实影响结果，不能只是界面标签。
- 公司成本口径必须由配置明确；验收固定采用 V2.4 样例口径：基本工资全额列示，无薪假单列减薪，单位成本等于应发加单位负担再减减薪类扣款。

### 6.6 假勤

- 工作日历、个人排班、获批申请和打卡记录共同形成时间事实。
- 同一员工同一时段不能同时被实勤、带薪假、无薪假、出差计勤和加班重复计算。
- 请假审批通过不等于最终计薪，需要根据有效计勤属性和净流水形成事实。
- 加班申请时长不等于最终支付时长，必须经实际确认；计薪与调休互斥。
- 跨月请假、销假和撤销按业务日期处理，余额流水和工资事实对应。
- 月结后发生变更时，下一工资草稿重算；已冻结或已发工资走更正。

### 6.7 审批与执行

- 审批同意只表示决定通过，不代表业务数据已写入成功。
- 审批对象必须校验业务类型、目标对象、内容哈希和预期版本。
- 提交后内容变化必须重新审批。
- 重复提交、审批、执行按幂等处理，不产生第二次记录、第二笔工资或第二个员工。
- 拒绝、退回、撤回保留原申请和历史，不直接删除业务记录。

### 6.8 展示与交互

- 统一使用 Element Plus；简单新增/编辑使用 Dialog，复杂表单使用 Drawer，复杂批次/详情使用独立工作区。
- 业务页面不得显示 `ACTIVE`、`MINOR_UNITS`、内部 ID、接口地址、ADR 编号、调试信息或技术异常堆栈。
- 员工、部门、岗位、合同、方案和角色关联使用对象选择器，不允许手输内部技术 ID。
- 列表必须支持真实查询、筛选、分页、状态、空态、加载态和错误态。
- 提交中防重复；失败保留可恢复输入；取消未保存内容需确认。
- 保存成功后返回列表时保留合理筛选和分页上下文。

### 6.9 生产初始化与升级

- 新库必须有一个启用超级管理员，必要的字典/目录/角色模板可存在，业务数据为零。
- 生产默认路径不得加载演示员工、演示工资或演示合同。
- 重复安装或重启不得新增管理员、重置密码或覆盖管理员配置。
- 升级必须前向执行并保留历史数据，不得自动清库。
- 生产安装脚本遇到演示模式、清库参数或缺失必要安全配置时必须拒绝。

### 6.10 验收

- 验收以用户可见业务结果为准，不以代码、接口存在或自动测试通过为准。
- 功能验收只能通过 Playwright MCP 模拟人为操作完成。
- 每个功能点必须有前置条件、操作路径、实际结果和证据。
- 未测试、无法执行或只有 mock/静态展示的功能不得判定通过。

## 7. 状态与生命周期

| 业务对象 | 初始状态 | 合法状态转换 | 禁止/终态 | 触发者 |
|---|---|---|---|---|
| 员工与任职 | 待入职/待生效 | 待生效 → 在职试用/正式 → 离职 → 归档；误归档可恢复 | 不删除历史；离职后不直接恢复为在职，重新入职新建雇佣事实 | HR、异动审批与执行、账号管理员 |
| 劳动合同 | 草稿/待登记 | 草稿 → 已登记 → 待生效 → 生效中 → 到期/终止；续签/变更产生新版本 | 不覆盖旧版本；终止不自动等于离职 | HR、合同审批与执行 |
| 请假/加班/出差等申请 | 草稿 | 草稿 → 已提交/待审批 → 已批准/拒绝/退回/撤回 → 已生效/确认 → 完成/取消/冲销 | 批准不等于已产生工资；已结算后不能直接改原单 | 员工、HR 代办、审批人、业务专员 |
| 考勤月结 | 未结 | 未结 → 预检 → 已结/锁定 → 重开 → 新版本已结 | 已锁定版本不得静默修改；重开不得改变已冻结工资 | 考勤专员、授权负责人 |
| 薪酬规则/方案 | 草稿 | 草稿 → 已验证 → 已发布 → 已退役 | 已发布不能原地改；退役不破坏历史重放 | 薪酬配置专员、发布人 |
| 员工薪酬档案 | 待配置 | 待配置 → 待生效 → 生效中 → 已结束/被新版本替代 | 同员工同期间不能冲突；历史版本不可覆盖 | 薪酬专员，调薪经审批 |
| 工资批次 | 准备中 | 准备中 → 输入冻结 → 试算 → 复核 → 批准 → 发放登记/工资条发布 → 完结 | 不跳步；已冻结不改输入；已完结不覆盖；更正另建 | 薪酬专员、复核人、批准人、发放/发布授权人 |

| 审批案例 | 待提交 | 待提交 → 待审批 → 已批准/拒绝/退回/撤回 → 效果待执行 → 成功/失败 | 批准不等于执行；重复决定不产生第二次效果；失败可重试 | 申请人、审批人、领域执行者 |
| 公告 | 草稿 | 草稿 → 待审核 → 已批准 → 已发布 → 已撤回/过期；模板可停用 | 未发布不可对受众展示；撤回后旧链接失效 | 公告编辑、审核人、发布人 |
| 绩效考核 | 草稿/未开始 | 未开始 → 进行中 → 自评/主管评价 → 校准 → 已发布 → 申诉中/已关闭 | 发布后冻结；修改走修订/申诉，不能直接覆盖 | 绩效专员、主管、员工、申诉处理人 |
| 招聘与录用 | 需求草稿/候选人入库 | 需求 → 审批 → 开放 → 暂停/关闭；候选人 → 面试 → Offer → 接受 → 转入职 | 未录用不进入员工/考勤/薪资；同一 Offer 不重复转入职 | 招聘专员、用人经理、审批人 |
| 培训场次 | 计划 | 计划 → 报名 → 进行中 → 完成/取消 | 未报名不能签到或考试；已完成签到/成绩/证书保留 | 培训专员、员工、讲师/考核人 |

通用规则：

- 状态转换只能由具备对应动作权限的用户或受控系统任务触发。
- 非法跳转必须拒绝并提示当前状态，不能静默成功。
- 回退必须通过退回、撤回、作废、重开、撤销、冲销或更正等明确动作。
- 已产生财务、考勤、审批或审计效果的状态为准终态，变更只能走可追溯补偿。

## 10. 边界情况

1. 新安装数据库没有业务数据时，页面显示真实空态和下一步配置入口，不显示假图表。
2. 同名员工、相同部门名称、多合同版本、多薪酬方案并存时，通过工号、部门、合同编号和生效期准确识别。
3. 合同、薪酬、参数、考勤或审批不完整时，正式工资批次阻断或进入有记录的授权例外。
4. 月中入职、离职、调部门、调岗或调薪时，按有效区间和规则分段，周期级税费/社保不重复。
5. 同一批次存在月薪员工和计时员工，各自使用自己的方案。
6. 请假撤销、销假、跨月、半薪、无薪和无需余额假别时，余额、考勤事实和工资一致。
7. 加班从计薪改调休或反向变更时，原支付和调休余额冲销，不允许同时保留两种结果。
8. 出差与请假、打卡、加班时间重叠时进入异常处理，不静默选择。
9. 工资草稿后源数据变化时提示过期；已冻结未批准显示影响并授权重开；已批准/发放生成更正。
10. 同员工同期间重复创建常规批次、重复计算、审批、发放或更正时只能有一个有效结果。
11. 多次更正只计算相对原结果和全部有效更正累计的增量；负数、未支付作废和已支付不回写原工资条。
12. 权限撤销、角色移除、账号停用或离职后旧页面、旧标签、旧通知和导出任务不能继续使用。
13. 批量导入或批量配置部分失败时，提交前预校验，提交后逐行显示成功/失败，不允许无提示半成功。
14. 编辑期间数据被他人修改或删除时提示版本冲突或不存在，不静默覆盖。
15. 历史工资条、合同、任职、审批和审计在升级后保持可查且金额/关联不漂移。
16. 生产已初始化后重启不新增管理员、不重置密码、不重复目录、不写 demo。
17. 生产尝试 demo/reset 或缺少安全配置时拒绝。
18. 外部设备、银行、税务或第三方系统不可用时明确“未启用/不可用”，不展示假成功。

## 11. 异常行为

1. **表单校验失败**：字段中文错误、聚焦首个错误、服务端复核、不写入。
2. **未登录或会话失效**：回登录页，不展示敏感数据。
3. **权限不足/对象越权**：统一 403/404，不泄露对象存在性，不写入。
4. **版本冲突**：提示“当前数据已更新，请刷新后重试”，保留已填内容，不静默覆盖。
5. **工资缺失或规则错误**：定位员工、期间、缺失项/规则项和来源，阻断该人或整批批准。
6. **冻结/批准/已完结数据被修改**：明确不可修改，引导重开、撤销或更正。
7. **重复操作**：返回已有结果或明确冲突，不产生第二份记录。
8. **部分成功**：显示总数、成功数、失败数、逐行原因，只重试失败项。
9. **查询/导出失败**：显示错误和重试入口，不显示为空列表，不伪造数据。
10. **来源系统不可用**：中文业务错误 + 关联标识，相关工资/审批/导出进入阻断。
11. **附件/导入失败**：说明类型、大小、行号或内容错误；确认前不写业务。
12. **撤权后的旧页面**：下一次操作被拒绝，敏感数据不能继续请求。
13. **数据不存在/已删除**：明确结果，不自动创建同名对象。
14. **系统内部错误**：业务页面显示中文错误和关联标识，不显示堆栈、路径、数据库信息或敏感值。

## 12. 保持不变

1. 单公司、内网、账号密码登录，不新增租户或强制 MFA。
2. 密码哈希、登录限流、账号停用、会话撤销、CSRF、服务端鉴权和敏感审计。
3. 历史工资条、合同、任职、假勤、审批和审计记录不被覆盖或删除。
4. 已批准、已发放或已冻结工资保持原金额和快照；新变更只走更正或新版本。
5. 升级已有数据库时，员工、合同、薪酬版本、工资条、角色和授权不丢失。
6. 原无权用户不会因页面重构获得额外菜单、动作、数据、字段或导出权限。
7. 已关闭的招聘、绩效、培训、公告和审批历史仍可查询且口径不变。
8. 生产初始化仍保持唯一管理员和零演示业务数据。
9. 历史工资、考勤、合同和审批的日期、金额和来源关联保持可核对。
10. 未经明确批准改变的业务规则和审批状态保持原有效果。

## 13. 非目标

1. 不建设多公司、多租户、SaaS 注册、订阅计费、租户切换或多法人账套。
2. 不强制或新增 MFA、短信、邮件验证码、SSO、LDAP、OIDC、企业微信扫码作为登录前置。
3. 不建设银行真实支付、税务申报、电子签章、电子合同法律审查、社保公积金真实申报或第三方财务自动对接。
4. 不建设完整通用 BPMN、任意低代码平台或可执行任意 PHP/JavaScript/SQL 的公式系统。
5. 不把外部考勤硬件、招聘平台、培训平台或身份系统的真实集成本身纳入本需求。
6. 不制定公司的法定工资、税费、社保或假期政策；通过可配置参数和规则管理。
7. 不为了页面数量保留全部旧菜单；旧路径可归并，但业务能力不得消失。
8. 不以自动单元测试、接口测试、脚本化 Playwright test 或静态检查替代人工验收。
9. 本阶段不输出代码修改方案、接口代码、数据库表结构实现或具体文件级实施计划。

## 14. 需求冲突

无未裁决需求冲突。

以下差异已按“用户明确指令 > V2.4 最新裁决 > V2.3 未冲突内容 > 历史版本”的顺序裁决：

1. **V2.4 文档标注“待确认”与用户要求“无需待确认”**  
   裁决：以用户指令为准，V2.4 的功能和系统边界作为确认内容；公司专属参数作为运行配置处理。

2. **页面归并可能删除旧入口与旧能力不能消失**  
   裁决：旧菜单和独立页面可以归并，但能力必须迁移到新页面、页签、动作或详情；通过授权跳转、能力映射或明确替代保证可达。

3. **V2.4 公司成本口径需业务确认与不设待确认问题**  
   裁决：系统支持可配置成本口径；验收采用 V2.4 假设样例和指定口径。样例不是公司法定政策。

4. **只能用 Playwright MCP 人工测试与现有自动化测试体系**  
   裁决：自动化测试可作为内部质量门禁，但不能作为本需求验收证据；模块签收和上线判定只接受 MCP 人工证据。

## 15. 待确认问题

无关键待确认问题。

公司实际计薪规则、社保费率、税费参数、假期额度、成本口径和业务日历属于运行配置数据，不属于阻塞本需求的产品决策；未配置时显示待配置并阻断相关计算，不使用虚假默认值。

## 16. 验收标准

### AC-01 范围与追踪完整性

**Given** 已取得 V2.0–V2.4 材料并锁定实际代码基线  
**When** 完成模块化盘点  
**Then** 21 模块、155 个历史入口、458 张功能卡、12 条跨模块闭环和 V2.4 T01–T24 均有唯一覆盖记录，包含当前状态、目标状态、入口、角色、权限、上下游和验收结论。

### AC-02 干净安装与升级

**Given** 一个空数据库和一个已运行旧库  
**When** 分别执行正式安装和升级  
**Then** 空库只产生必要元数据和一个启用超级管理员、零业务数据；重复启动不重复创建或重置密码；旧库升级后核心数据数量与核对结果一致；生产 demo/reset 被拒绝。

### AC-03 登录、角色与对象主体

**Given** 超级管理员、HR、考勤专员、薪酬专员、复核人、部门经理和员工账号  
**When** 各角色登录并从菜单进入工作台  
**Then** 只显示其有权页面、动作和数据；密码登录可用；未绑定员工的管理员不能进入本人申请；员工自助固定本人；撤权后下一次操作立即生效。

### AC-04 员工、组织、岗位与合同闭环

**Given** 新员工和已存在部门、岗位  
**When** 创建员工、绑定任职、登记合同并配置初始薪酬  
**Then** 员工、任职、合同和薪酬引用同一员工和一致有效期；失败无半条记录；员工详情、合同详情和薪酬档案显示同源版本；同名不误绑。

### AC-05 权限与字段隔离

**Given** 用户有页面权限但无动作、薪资字段或部门范围  
**When** 通过菜单、直接地址、隐藏按钮、选择器或导出尝试访问  
**Then** 服务端正确限制页面、动作、对象、字段和导出；不泄露存在性、工资、证件或他人数据；撤权后旧标签立即失效。

### AC-06 同批次多方案

**Given** 员工 A 使用月薪方案，员工 B 使用计时方案  
**When** 在同一工资批次核算  
**Then** A 和 B 分别使用自己的合同、方案和参数；批次级设置不能覆盖个人方案；合计等于逐人明细之和。

### AC-07 主计薪样例

**Given** 员工 A 基本工资 8000 元，计划工作 20 天，无薪假 1 天，餐补 20 元/天且实际计薪 19 天，已确认加班 8 小时，时薪基数 50 元、倍率 1.5，绩效奖金 500 元，个人社保 600 元、公积金 300 元、个税示例 100 元，单位负担 900 元  
**When** 使用“基本工资全额＋单列无薪假扣款”的测试方案试算并完成批次计算  
**Then** 显示基本工资 8000.00、餐补 380.00、加班费 600.00、绩效奖金 500.00、应发 9480.00、无薪假扣款 400.00、个人扣款合计 1400.00、实发 8080.00、公司成本 9980.00；每项可展开来源和公式。

### AC-08 请假取消与动态重算

**Given** 员工 A 有一笔已批准无薪假，工资草稿已生成  
**When** 撤销请假并实际补足出勤，然后刷新工资草稿  
**Then** 余额回补，餐补变为 400.00，无薪假扣款变为 0，其他测试项不变，实发变为 8500.00；若未实际出勤，按缺勤处理。

### AC-09 月中调薪分段

**Given** 20 个计划工作日中，前 10 天月薪 8000 元、后 10 天 9000 元  
**When** 执行有效调薪并计算当月工资  
**Then** 基本工资为 8500.00，不是 9000.00，也不是两套全月工资相加；审批前不生效；未来日期不提前；月度税费和社保只执行一次。

### AC-10 加班、调休与出差互斥

**Given** 同一员工存在已确认加班、调休选择、出差计勤或打卡事实  
**When** 变更加班结算或登记出差  
**Then** 工资和调休余额只产生一种对应结果；出差、请假、打卡、加班不重复占用时间；重复确认/结算不产生第二笔金额或额度。

### AC-11 规则配置校验

**Given** 薪酬专员创建草稿项目、方案或规则  
**When** 配置固定值、比例、条件、阶梯、组合公式、未知变量、循环依赖、类型错误或除零  
**Then** 合法规则可试算、发布并被真实计算消费；非法规则在发布前阻断并定位项目和变量；已发布版本不能原地修改。

### AC-12 多次更正

**Given** 原工资实发 8080 元，首次更正目标 8300 元，第二次目标 8350 元  
**When** 依次执行两次有效更正  
**Then** 第一次差额 220 元，第二次差额 50 元，累计 8350 元，不是 270 元；原工资条不变；重复提交不重复支付；已支付更正不能普通编辑覆盖。

### AC-13 审批与执行一致性

**Given** 需要审批的调薪、请假、离职、合同终止或工资批次  
**When** 发起、审批、执行，随后重复提交或执行  
**Then** 审批决定和领域结果分别可查；批准后内容变化需重新审批；重复决定/重放只返回已有结果或明确冲突。

### AC-14 福利、绩效与工资联动

**Given** 员工 A、B 参保组合不同，A 有已批准并按规则映射的绩效结果  
**When** 计算工资  
**Then** 个人社保/公积金和单位成本按各自参数计算；已批准且映射的绩效进入正确工资项；未批准、未映射或草稿结果不进入工资；费率更新不改历史工资条。

### AC-15 招聘、培训与员工档案

**Given** 候选人完成 Offer 并被录用  
**When** 执行录用转入职，随后完成培训和绩效记录  
**Then** 同一 Offer 只创一个员工和一条雇佣关系；招聘、员工、合同和薪酬首月链路可追溯；培训记录只来源于有效报名、签到和考试；未配置培训津贴不产生工资副作用。

### AC-16 仪表盘、报表与导出

**Given** 已有员工、组织变动、合同、假勤、工资和招聘数据  
**When** 在首页或报表中心筛选、下钻、导出  
**Then** 汇总、明细和工资条一致；历史组织归属不随当前调岗漂移；导出再次鉴权；无权用户看不到金额列或不能下载；失败不显示空数据。

### AC-17 公告、通知与撤权

**Given** 公告已发布或工资条已发布并触发消息  
**When** 用户打开通知，随后被撤权、公告撤回或链接过期  
**Then** 只有有效受众可查看；重复投递不重复；工资通知不暴露金额；旧链接不能再访问敏感内容。

### AC-18 统一界面与中文

**Given** 业务用户进入任意列表、详情、表单、抽屉、报表和选择器  
**When** 使用增删改查、筛选、分页、空态、加载、错误和权限差异  
**Then** 不出现原始枚举、内部 ID、接口地址、调试信息或技术堆栈；金额按元显示两位小数；日期按公司时区；关联对象使用选择器；提交防重复，失败保留输入，成功后刷新并保留列表上下文。

### AC-19 异常和边界

**Given** 数据缺失、对象不存在、版本冲突、重复操作、权限变化、来源不可用或部分失败  
**When** 用户操作  
**Then** 系统给出可理解中文结果和可恢复动作；不产生无提示半成功、不伪造零、不覆盖冻结数据、不重复写入；刷新后看到真实持久状态。

### AC-20 历史与回归不变

**Given** 已有历史员工、合同、假勤、工资条、角色和审批  
**When** 完成整改并升级  
**Then** 历史金额、版本、来源、审计和权限未被无授权修改；已完成流程保持原效果；历史工资条可按原规则和快照重放；升级前后核对有记录。

### AC-21 全后台 Playwright MCP 人工验收

**Given** 已形成覆盖 21 模块、155 历史入口、458 功能卡、当前实际页面动作和 V2.4 T01–T24 的验收清单  
**When** 验收人员使用 Playwright MCP 以真实角色登录隔离环境  
**Then** 逐项完成导航、查询、筛选、分页、表单、提交、取消、审批、刷新、重新登录、权限差异和异常操作；每项有执行证据和 PASS/FAIL/BLOCKED 结论；未执行项不得判通过；不用机械自动化测试或静态检查替代。

### AC-22 最终发布判定

**Given** 所有模块和跨模块验收完成  
**When** 汇总缺陷、阻断项、权限泄漏、工资对账和演示数据检查

## 2. 当前系统

### 2.1 当前流程

#### 2.1.1 登录与权限

```text
登录页
→ POST /v1/auth/login
→ AuthController
→ LoginService / SessionManager
→ 服务端 Session + HttpOnly Cookie
→ GET /v1/me/permissions
→ PermissionProjection
→ AuthorityBinding + role_pages
→ 前端 session store
→ 路由守卫检查 page_code + required_capability
→ 页面按钮 session.can()
→ 后端 RequireCapability
→ Controller / Service
```

主要事实：

- 角色、页面、能力、anchor、字段档位均有模型。
- 部分标准角色的页面授权与能力授权不匹配。
- 页面 required capability 与动作清单分离。
- `PAYROLL_RUN` 授权要求请求者已是成员，但复核/批准/发布人员在操作前尚未进入成员集合。
- 部分 Controller 只检查 capability，没有执行 `Authorizer::constrain()`。
- 数据范围和字段策略尚未完全参与真实授权。

#### 2.1.2 员工、组织、合同与异动

```text
员工列表新增
→ EmployeeCreateDrawer
→ POST /v1/employees/onboard
→ CreateEmployeeService
→ persons + employments + assignments + employment_terms
```


```text

```

```text

→ TravelService
→ business_trip_records / travel_attendance_links / travel_expenses
```

当前断点：

- 请假和补卡 Workflow 模板使用 `workflow.noop`，Time 未注册领域 Effect。
- 加班申请没有审批，创建即 `APPROVED`。
- PAY/TIMEOFF 结算没有写工资输入或调休账本。
- Payroll 读取 `attendance_days.overtime_minutes`，与加班审批/结算脱节。
- 出差链接只用于日历，不生成计薪事实。
- 考勤重算接口只返回 202。
- 请假带薪属性依赖 code。
- Payroll 只读 `CONSUME`，忽略 `REVERSE`，跨月请假归期错误。
- 月结不冻结工资输入。
- 冻结保护只覆盖少数撤销路径。

#### 2.1.4 薪酬

```text
项目/方案
→ PayrollCatalogController
→ PayrollItemService / PayrollRunService
→ payroll_items / payroll_item_versions / payroll_schemes / payroll_scheme_items

员工薪酬/调薪
→ CompensationController
→ CompensationService
→ employee_compensations / salary_adjustments

批次
→ PayrollRunService
→ SnapshotService
→ PayrollInputDirectory + EmploymentTermsDirectory
→ payroll_input_snapshots

计算
→ CalculationService
→ PayrollCalculator
→ payroll_run_employees / payslips / payslip_lines
```

当前事实：

- 一个批次只有一个 `scheme_id`。
- 计算实际使用 `employment_terms.base_salary_minor`。
- `employee_compensations` 和 `salary_adjustments` 基本不影响工资。
- 项目计算类型、公式、比例、basis、taxable 等大量配置未真实参与计算。
- 缺考勤返回全 0，可能按满勤计薪。
- 只取月末一个 Terms 版本，不支持月中分段。
- 个别员工失败时，只要有一人成功整批仍可能进入 `CALCULATED`。
- 更正基线只取原批次，YTD 用可变汇总和 `max(0, ...)`。
- 发布、发放、工资条发布是单一状态链，不能独立。
- 更正、重开、取消缺少 UI 入口。

#### 2.1.5 人才、福利、报表与平台

- 福利交易存在，但不进入薪酬计算；`payroll_run_id` 唯一约束与多人多计划冲突。
- 绩效结果可发布，但没有奖金映射和工资输入。
- Offer 薪资没有进入初始薪酬配置；候选人申请列表接口缺失。
- 培训考试结果、员工培训档案和导出不完整。
- 通知可把投递直接标记为 `SENT`，外部通道实际是日志桩。
- Reporting 有定义、运行、导出和签名下载骨架，但薪酬成本投影不可用，字段/数据权限不完整。
- 默认 Seeder 调用 demo；安装器包含非必要业务参数；权限目录同步可能删除自定义页面授权。
- 当前本地 SQLite 迁移不完整。

### 4.4 冲突

Requirement 本身无待确认冲突；当前实现与 Requirement 有以下硬冲突，技术设计按 Requirement 修正：

1. **工资唯一事实**：当前从 `employment_terms` 取工资，而 Requirement 要求 Payroll 执行薪酬唯一。
2. **统一生命周期入口**：当前员工建档、部门调动、合同变更可绕过 Lifecycle，而 Requirement 要求单据和生效时间驱动。
3. **计算配置真实性**：当前大量薪酬配置只存不算，而 Requirement 要求配置真实进入计算。
4. **缺失数据不能变零**：当前缺考勤/失败员工可被零化，而 Requirement 要求阻断或授权例外。
5. **审批执行闭环**：当前部分审批通过但无 Time 效果，Requirement 要求审批后领域执行可追踪。
6. **发布和发放独立**：当前单状态链不能表达独立发布/发放，Requirement 要求两者分离。
7. **干净初始化**：当前默认 Seeder 调用 demo，Requirement 要求生产零演示数据。
8. **全功能人工可验收**：当前后端有更正/重开/取消等能力但无 UI，Requirement 要求管理后台功能点可执行。

| 公告、消息、投递 | Engagement | 只读业务事件 ID/版本 |
| 报表、投影、导出 | Reporting | 只读 |
| 审计、Outbox、幂等、文件、安装 | Platform | 横切基础设施 |

#### 5.1.2 员工、合同和薪酬数据链

```text
Person
→ Employment
→ Assignment（有效期）
→ EmploymentContract
→ EmploymentContractVersion（约定版本和约定薪酬）
→ EmployeeCompensationVersion（实际执行薪酬）
→ SchemeVersion + RuleVersion + 参数覆盖
→ PayrollRunEmployee + InputSnapshot
```

- 合同版本 append-only，带员工、合同 ID、有效期、附件/条款快照、约定薪酬摘要和来源。
- 合同 `DRAFT` 可激活；未来生效合同在生效日前不参与实际工资。
- 员工薪酬版本增加合同版本、方案版本、参数覆盖、有效期、状态、批准案件和内容 hash。
- 同员工同一天不能有重叠薪酬版本；新版本不覆盖旧版本。
- `employment_terms` 保留非薪酬条款和历史兼容字段，新流程不再用它保存执行工资。
- 历史工资字段迁移到员工薪酬版本；缺合同/方案/唯一有效期时标 unresolved，禁止自动取第一条。

#### 5.1.3 薪酬规则

- `payroll_item_versions` 继续表示薪资项目不可变版本。
- 新增规则版本，保存受限 AST、阶段、依赖、条件、舍入、单位、引擎版本、hash 和状态。
- 方案项引用具体规则版本和项目版本，不只用标签。
- 方案发布后不可原地修改；变更产生新版本。
- 规则仅允许白名单变量、运算、条件、`MIN/MAX/ROUND`、显式集合、阶梯和受控福利/税务函数。
- 禁止 eval、脚本、网络、文件、数据库查询、随机数和系统时间。
- 金额整数分；比例使用定标整数/小数串；计算轨迹记录输入、条件、舍入和结果。

#### 5.1.4 工资批次和快照

- `payroll_runs` 不再由全局 `scheme_id` 决定所有员工方案；旧字段仅用于历史兼容。
- 新增 `payroll_run_members`：preparer、reviewer、approver、disburser、publisher 和分配依据。
- `payroll_run_employees` 增加合同/薪酬/方案版本、快照、阻断原因、目标额和差额。
- `payroll_input_snapshots` v2 包含：
  - 员工和任职期间
  - 合同版本
  - 员工薪酬版本
  - 方案/规则/项目版本
  - 已关闭 Time 事实版本
  - 福利输入
  - 绩效结果和映射
  - 一次性奖扣
  - 法定参数版本
  - 来源 ID/版本/hash
  - completeness、缺失项、不适用项
- 锁定后不读取当前合同、方案、福利参数或考勤。
- 员工快照唯一键、hash、版本沿用现有模型。

#### 5.1.5 时间事实

- 保留 `punch_records`、`attendance_days`、请假账本和加班确认作为操作事实。
- 增加月度时间事实版本和逐日/区间事实行：
  - employment、业务日期/区间
  - scheduled/worked
  - 带薪/部分薪/无薪假
  - 分类加班
  - 出差计勤方式
  - 来源单据、版本、审批状态、修订序号
  - source hash、生成时间
- 月结生成不可变事实版本；Payroll 只消费已关闭版本。
- 已关闭月份修改必须重开并生成新版本。
- 假期规则版本增加计薪属性，不能按 code 猜。
- 加班 PAY 和 TIMEOFF 互斥；调休用 append-only 账本。
- 出差计勤进入同一事实，不直接写工资。

#### 5.1.6 更正和 YTD

- 新增 `payroll_ytd_ledger`，每次批准/发放的 YTD 增量 append-only 保存。
- `payroll_ytd` 仅作汇总投影，可由 ledger 重算。
- ledger 记录员工、税年、来源 run、类型、金额字段、符号、时间和 hash。
- 负更正不得 `max(0)` 截断；负数 carry-forward 明确处理并展示。
- 更正批次记录原始批次、此前有效更正、原期间、结算期间、目标额、累计已批准额、本次差额。
- 更正使用原计薪期间事实和明确知识时点，不混用“原条款 + 新月份考勤”。
- 更正唯一约束覆盖原始 run、员工、目标期间和有效更正序号。

#### 5.1.7 福利、绩效和招聘

- 福利交易支持一员工一期多计划，移除 `payroll_run_id` 唯一限制，增加冲销和状态。
- Benefit 缴费通过授权输入端口进入 Payroll 快照，Payroll 不直读 Benefit 表。
- 绩效结果增加数值分数、等级和来源 revision；奖金映射保存映射版本、周期、发放期间。
- 未批准、未映射、草稿、跨周期结果不生成工资变量。
- Offer 保存约定工资和方案建议；录用转入职通过 Payroll 命令创建薪酬草稿。
- 培训考试增加报名、考试版本、作答/成绩、通过状态和来源。

#### 5.1.8 权限和安装

- 页面、动作、能力、锚点、字段构成单一代码目录，前端 manifest 与服务端 catalog 一致。
- 角色保存原子提交页面、页面读取能力、动作、数据范围、字段档位。
- 页面授权或能力缺失，服务端和前端均不可用。
- 工资批次成员与能力授权分离；能力决定职责，成员关系决定具体批次。
- 生产安装只写 schema、元数据、必要字典和唯一管理员，不写业务数据或 demo。
- 权限目录 upsert，不删除自定义角色页面。
- 健康检查校验迁移、安装状态和管理员状态。

### 5.2 核心业务流程

#### 流程 A：员工入职与建档

```text
发起入职
→ 校验能力、组织范围、岗位、入职日期
→ 创建 Lifecycle Onboarding Case/Intent
→ Workflow 审批
→ Onboarding Effect（LOCAL，同一事务）
→ People CreateEmployeeCommand
→ Person + Employment + Assignment + 任職条款
→ 可选创建合同/薪酬待办
→ 发布 employment_id、合同版本、薪酬版本
→ 通知和审计
```

规则归属：

- 权限：IAM middleware + Authorizer + 组织范围。
- 审批状态：Workflow。
- 员工/任职事实：People 命令。
- Effect 幂等：Lifecycle/Workflow。
- Effect 失败：Case 保持决定事实，Effect 标 `FAILED`，Lifecycle 同步失败并显示可重试。

#### 流程 B：合同与薪酬配置

```text
员工详情/合同台账
→ 选择员工、有效合同、方案版本
→ 校验合同版本同员工、同任职、有效日期
→ 创建/激活合同版本（必要时审批）
→ 创建 EmployeeCompensationVersion
→ 校验方案已发布、个人参数合法、无重叠
→ 产生生效段
→ 员工详情、合同详情、薪酬档案读取同一版本 ID
```

合同约定金额与实际执行金额可以不同，页面显示两者及关联，不用实际薪酬覆盖已签署约定。

#### 流程 C：时间事实到工资

```text
打卡导入/补卡/请假/加班/出差
→ Time 审批与 Effect
→ 更新账本/申请/确认事实
→ 月结预检
→ 生成 time_payroll_fact_version
→ 输出已关闭事实版本
→ Payroll 生成员工快照
```

- 请假审批产生净流水和考勤事实。
- 销假写 REVERSE/RELEASE，回补余额和事实。
- 加班确认产生 PAY/TIMEOFF 唯一选择。
- 出差审批生成计勤区间，不造假打卡。
- 月结冻结事实和 hash；后续变更重开并生成新版本。

#### 流程 D：薪酬批次

```text
创建批次（期间、发放期、范围）
→ 预检员工/合同/薪酬/时间/福利/绩效
→ 解析每个员工有效合同、方案、规则、参数
→ PayrollInputSnapshot v2
→ 锁定
→ 异步逐员工计算
→ 汇总成功/异常
→ 复核
→ 提交审批
→ Workflow Effect
→ 批准
→ 发放登记 / 工资条发布（独立）
→ 完结
```

- 任一员工有阻断异常，批次不得进入审批。
- 异常显示员工、项目、原因和来源。
- 计算、审批、发放重试按 run + employee + operation 幂等。
- 完成前禁止重算已冻结结果。

#### 流程 E：更正

```text
已发布/已发放工资
→ 授权发起更正
→ 原批次、原因、结算期间
→ 读取原计薪事实和当前有效更正
→ 重新计算目标结果
→ 计算本次差额
→ 更正批次
→ 复核/审批
→ 发放登记/发布
→ signed YTD ledger
```

更正不得覆盖原工资条、不得重算成新原批次、不得重复支付此前差额。

#### 流程 F：权限变更

```text
管理员编辑角色
→ 选择页面、动作、范围、字段
→ 服务端校验页面 required capability 和动作
→ 原子保存角色配置和编译后的 bindings
→ 提升受影响用户 auth_version
→ 撤销/刷新会话和权限快照
→ 前端重新获取 /me/permissions
→ 旧页签下一次请求按新权限拒绝
```

### 5.3 状态设计

#### 5.3.1 工资批次

将主状态与发布/发放状态解耦：

| 状态 | 进入条件 | 可执行动作 | 禁止 |
|---|---|---|---|
| `DRAFT` | 创建批次 | 预检、编辑范围、取消 | 计算、审批 |
| `INPUT_LOCKED` | 快照完成且 hash 生成 | 试算、重开、取消 | 修改输入 |
| `CALCULATING` | 异步试算开始 | 查看进度、失败重试 | 修改快照、审批 |
| `CALCULATED` | 全员计算成功 | 复核、退回 | 未复核直接批准 |
| `CALCULATED_WITH_BLOCKERS` | 至少一名员工阻断 | 查看异常、修复、重试 | 复核、批准、发布、发放 |
| `REVIEWED` | 复核人通过 | 提交审批、退回 | 跳过审批 |
| `APPROVED` | Workflow 审批 Effect 成功 | 发放登记、工资条发布、关闭 | 修改金额或重算 |
| `CLOSED` | 发放登记和工资条发布均完成 | 只读、审计 | 重开；更正另建 |

独立状态：

- `payslip_status`: `UNPUBLISHED / PUBLISHED`
- `disbursement_status`: `NOT_REGISTERED / REGISTERED`
- `correction_status`: `NONE / DRAFT / IN_PROGRESS / APPROVED / APPLIED`

合法转换：

```text
DRAFT
→ INPUT_LOCKED
→ CALCULATING
→ CALCULATED / CALCULATED_WITH_BLOCKERS

CALCULATED
→ REVIEWED
→ APPROVED
→ CLOSED

审批前状态
→ CANCELLED

INPUT_LOCKED / CALCULATED / REVIEWED
→ DRAFT 或 INPUT_LOCKED（获权重开并生成新快照）

APPROVED
→ 新更正批次
```

禁止：跳过复核/批准、已批准改金额、带阻断异常进入复核、已发布覆盖原工资条、同员工同期两个有效常规批次或有效更正差额。

#### 5.3.2 规则、合同和薪酬版本

```text
规则：DRAFT → VALIDATED → PUBLISHED → RETIRED
合同：DRAFT → PENDING_EFFECTIVE → ACTIVE → TERMINATED / EXPIRED / ARCHIVED
薪酬：DRAFT → PENDING_APPROVAL → SCHEDULED → ACTIVE → SUPERSEDED / ENDED
```

- 规则发布版本不可改；退役不破坏历史重放。
- 合同 `EXPIRING/EXPIRED` 可由日期派生，减少状态漂移。
- 同员工同一天不能有重叠有效主合同。
- 未来薪酬版本按时生效，不提前应用。
- 旧薪酬版本被新版本自然结束，不覆盖。

#### 5.3.3 申请、月结和审批

```text
申请：DRAFT → SUBMITTED → IN_REVIEW → APPROVED/REJECTED/RETURNED/WITHDRAWN
→ EFFECTIVE/CONFIRMED → COMPLETED/CANCELLED/REVERSED

月结：OPEN → CLOSING → CLOSED（事实版本+hash）→ REOPENED（新版本）→ CLOSED
```

- 审批通过不等于 Time 事实已写入。
- 已结算后取消走冲销或新更正。
- 跨月申请按天拆分。
- Payroll 只使用已关闭事实版本；重开需要原因、权限和审计。

Workflow 沿用 Case/Decision/Effect 状态；业务对象必须同时显示申请状态、审批状态和执行状态。

### 5.5 API 设计

| 接口域 | 设计 | 权限/校验 | 幂等/错误 |
|---|---|---|---|
| `/v1/me/permissions` | 复用，返回页面、动作、字段和对象能力摘要 | 仅本人 | 权限快照失败明确报错，不自动放行 |
| 页面动作目录 | 扩展 `/v1/pages/catalog` 或统一 catalog，返回 required capability、动作、anchor、字段 schema | `iam.permission.read` | 只读；与前端 manifest 构建校验 |
| 角色授权 | 复用 `PUT /v1/roles/{id}/authorization`，输入页面、动作、范围、字段和 expected version | `iam.role.manage`，校验可授予范围、SoD、最后管理员保护 | 事务保存；重复 Idempotency-Key 回放；版本冲突 409 |
| 用户角色 | 复用用户管理接口，查询过滤有效角色和 auth_version | `iam.user.manage` / `iam.role.manage` | 变更后立即刷新授权版本 |
| 员工建档 | `POST /v1/lifecycle/onboarding` 主入口，内部调用 People CreateEmployeeCommand | `lifecycle.onboarding.manage` + 组织范围 | Idempotency-Key；原子创建；返回 case、employment、待办 |
| 员工变更 | 保留 Lifecycle 类型入口；不保留可直接写 Assignment/Terms 的 UI 路径 | 对应 capability + 源/目标组织 | Case 唯一、Effect 幂等、重复返回原结果/409 |
| 合同 | 复用合同列表/详情；创建后待生效，变更/续签/终止形成 Case；增加激活 | `people.contract.*` / `lifecycle.contract.manage` | 同员工有效期唯一，跨员工拒绝，旧版本不可覆盖 |
| 员工薪酬 | 扩展 `/v1/payroll/compensations`：员工、合同版本、方案版本、参数、effective_from、expected_version | `payroll.compensation.manage` + P3 审计 | 无重叠；同员工同日期唯一；重复回放/409 |
| 薪酬项目 | 复用项目/版本接口；增加发布/退役 | 配置/发布分离 | 已使用版本不可改；版本自增 |
| 薪酬方案 | 复用方案接口；新增 validate、simulate、publish、retire | 配置/发布分离 | 规则错误返回项目和变量，禁止发布 |
| 调薪 | 复用调薪申请，必须绑定 Workflow；批准后只创建薪酬版本 | `payroll.salary-adjustment.manage` | 一 Case 只生效一次；版本冲突 409 |
| 工资批次 | `POST /v1/payroll/runs` 输入期间、发放期、范围，不再由单方案决定所有人 | `payroll.run.prepare` + 范围 | 同期间常规批次唯一 |
| 批次输入 | `POST /runs/{id}/prepare-inputs`、`GET /runs/{id}/exceptions` | prepare + PAYROLL_RUN | 返回完整员工/缺失项/来源；不静默跳过 |
| 锁定/试算 | `POST /runs/{id}/lock-inputs`、`POST /runs/{id}/calculate` | prepare + run member | 异步 202；状态错误 409；重试按员工/批次幂等 |
| 复核/审批 | `POST /runs/{id}/review`、`POST /runs/{id}/submit-approval`，审批通过 `POST /cases/{id}/decisions` | review/approve 分离，SoD policy | Effect 失败可诊断，不返回成功状态 |
| 发放/发布/关闭 | `POST /runs/{id}/register-disbursement`、`publish-payslips`、`close` | 独立 capability + 成员 | 独立状态；重复幂等；未满足条件 409 |
| 更正/重开 | `POST /runs/{id}/corrections`、`POST /runs/{id}/reopen` | correct/reopen + 状态/原因 | 仅规定状态；更正唯一键；禁止重复差额 |
| 工资条 | `GET /v1/payroll/payslips/me`、`GET /payslips/{id}`，含明细和来源 | SELF 或管理授权；已发布才可见 | 未发布 403/404；字段按 P3 裁剪 |
| 福利 | 复用 plans/enrollments/transactions；增加终止/冲销 | `benefit.*` + 行级范围 | 员工仅本人；一期多计划 |
| 请假 | 复用申请/预览/取消；代申请预览统一 target preview | Time capability；actor/subject 分离 | 余额/重叠/冻结校验；跨月净额 |
| 考勤月结 | 复用 closings，返回 fact_version、source_hash、异常数 | attendance manage/reopen | 关闭只读；重开新版本 |
| 加班/调休 | 复用申请/确认/结算；增加结算冲销 | overtime capability | PAY/TIMEOFF 互斥，唯一结算 |
| 出差 | 复用申请/变更/销单；审批统一 Workflow；费用只做内部台账 | time.travel.* + 对象范围 | 变更审批；销单更新事实 |
| 招聘 | 补 `GET /v1/recruitment/candidates/{id}/applications`；Offer 转补偿走统一入职 | recruitment capability + 组织范围 | 一次 Offer 只转一次 |
| 绩效 | 复用周期/评分/发布；发布生成不可变结果；增加工资映射约束 | 绩效范围 + result.publish | 草稿不发布；申诉回写 |
| 培训 | 复用计划/场次/报名/签到；增加考试结果和档案读取 | 培训范围；SELF 仅本人 | 未报名不能考试；成绩绑定版本 |
| 通知 | 复用通知列表/已读；外部投递只有实际成功才 SENT | 本人消息；管理投递需 template/delivery | 重复投递幂等，失败可重试 |
| 报表/导出 | 复用运行和导出；增加字段裁剪、主体版本和真实投影 | `reporting.report.read` / `export` | 导出重新鉴权；失败不显示空表 |
| 设置/安装 | 复用命令和 API；增加安装状态/升级检查 | system admin | 生产拒绝 demo/reset；重复安装幂等 |

统一错误语义：

- 422：字段校验失败。
- 401：未认证。
- 403/404：无权限或对象越界，不泄露存在性。
- 409：状态不允许、版本冲突或幂等冲突。
- 503：来源不可用。
- 所有有重复风险的写命令要求 `Idempotency-Key`；重复返回原结果并标 `Idempotency-Replayed`。
- 详情响应增加 `state`、`version`、`allowed_actions`、`source_version`。

### 5.6 前端设计

#### 页面入口

保持 21 模块工作区，不恢复 155 个菜单。继续以现有约 37 个入口为基础，按业务对象聚合，详情保留深链接。

重点页面：

- `/workspace`：我的待办、申请、合同摘要、考勤、工资条、培训绩效。
- `/hr/employees`、`/hr/employees/:id`：列表、详情、合同/薪酬摘要、入职、导入、变更。
- `/hr/movements`：全部异动类型统一台账和发起。
- `/hr/contracts`、详情：登记、激活、续签、变更、终止。
- `/attendance`、`/leave`、`/overtime`、`/travel`：本人和管理页签。
- `/payroll`、`/payroll/runs/:id`：项目/方案/薪酬档案、批次、异常、复核、审批、发放、发布、更正、工资条。
- `/benefits`：参数、参保、福利交易。
- `/performance`、招聘、培训、公告、审批、权限、设置、审计。

#### 页面状态

统一支持：

```text
loading / empty / error / forbidden / partial / success / conflict
```

- loading：骨架或加载提示。
- empty：真实无数据，不伪造图表。
- error：中文错误和 request_id。
- forbidden：无权限，不泄露对象存在性。
- partial：来源部分不可用或投影不完整，显示截止时间。
- success：刷新服务端真实结果。
- conflict：保留输入，提示刷新和版本差异。

#### 数据来源和同步

- 通过 typed API client / 生成类型访问，不直接拼 URL 或 fetch。
- 页面权限来自 `/me/permissions`；动作可见性以服务端 `allowed_actions` 为准。
- 保存后重读详情和列表摘要，不依赖本地假成功。
- 返回列表保留筛选、分页、排序和选中。
- 权限变化后刷新 session/permissions，旧页签下一次写请求被拒绝。
- 对象版本冲突不静默覆盖。

#### 组件和交互

复用 `PageShell`、`DataTable`、`FormDrawer`、`FormDialog`、`MoneyText`、`StatusBadge`、`Timeline`、`MaskedField`、加载/空/错组件、`ActionGate`、角色授权组件。

需要修改：

- `MoneyText` 使用精确字符串/BigInt，支持公司币种。
- `format.ts` 移除浮点金额除法。
- `ActionGate` 不展示内部 capability。
- 所有详情页补充动作清单。
- 工资批次增加异常、更正、重开、取消、发布、发放独立状态。
- 员工自助工资条接入 `/workspace` 或独立自助入口，不进入管理 `/payroll`。
- 增加未保存离开提示、提交防重复和刷新状态恢复。

#### Playwright MCP 验收

- 真实 `VITE_API_MODE=http` 前端 + Laravel 后端。
- 不使用默认 mock。
- 干净安装或明确迁移的隔离库。
- 角色独立账号，避免登录限流误判。
- 不使用自动 Playwright test 结果替代人工 MCP。
- 每功能点保存截图/快照、角色、路径、前置数据、操作和结果。
- loading/empty/error/forbidden/partial 全部人工模拟。

### 5.7 后端设计

#### 分层职责

- Controller：鉴权上下文、请求映射、应用命令、统一响应。
- Application Service/Command：事务、幂等、跨域编排、Effect。
- Domain Service：状态机、版本解析、金额计算、规则执行、来源校验。
- Repository/Model：持久化；禁止跨模块 Model 直接写表。
- Workflow Effect Handler：把审批结果转为领域命令；不直接写业务表。

#### 事务边界

- 员工建档：Person、Employment、Assignment、Terms 同一事务。
- 合同创建/激活/变更：合同、版本、来源关联同一事务。
- 薪酬版本：薪酬版本、来源案件、审计、Outbox 同一事务。
- 批次锁定：快照、hash、run 状态同一事务。
- 本地审批 Effect：Decision/Effect 状态与领域写入同一事务；外部/延时 Effect 走可重试 Job。
- 试算：员工结果独立可重试，批次聚合和状态转换在批次级事务；长任务异步。
- 更正：更正链接、明细、累计差额、YTD 来源同一事务。
- 发布/发放：各自独立事务。

#### 并发和幂等

- 版本更新使用 expected version/乐观锁，冲突 409。
- 员工/合同/薪酬同生效日唯一键防重复。
- 批次和员工结果唯一键防重复计算。
- 同员工同期有效常规批次唯一。
- 同员工同原始批次有效更正唯一差额。
- Workflow 重复决定/Effect 不重复执行。
- 有副作用命令进入 `CommandRunner`，覆盖薪酬、假勤、异动、合同、审批、发放、更正和导出。

#### 异常和事件

- 业务错误统一错误码；中文消息与 request_id 分离。
- Effect 失败保留错误、重试次数和可恢复状态；业务对象显示“审批通过但执行失败”。
- Outbox 只记录 ID、版本和事件类型，不写金额/敏感值。
- 订阅事件失败不阻断主事务，但必须有重试和告警。
- 定时任务覆盖到期合同、Workflow 到期/延时 Effect、Outbox 发布、通知重试和报表订阅。

### 5.8 兼容 / 迁移

#### 历史数据

- `employment_terms` 历史工资字段保留原值，不回写或销毁。
- 迁移到员工薪酬版本时，缺合同/方案/唯一有效期标 unresolved，不取第一条、不按金额猜测。
- 现有 `employee_compensations` 保留；补齐合同/方案关联时验证同员工和有效期。
- 现有合同版本缺合同 ID 的，唯一匹配才回填，否则保留待裁决。
- 现有工资条、快照和更正保持；新规则只作用于新批次或授权重开的新快照。
- 现有 YTD 汇总迁移为 signed opening ledger；金额和来源可核对。
- 历史请假类型无计薪属性时标 `UNRESOLVED`，历史工资不回算；新申请配置前阻断。
- 既有月结无事实快照时，仅未冻结批次允许重开/重算；已发布工资使用原快照。

#### 老接口和老页面

- 155 个历史入口按 V2.3/V2.4 的保留、合并和替代关系迁移。
- 被合并旧页面通过授权跳转到目标页面/Tab；不保留第二套 UI，不静默丢失能力。
- 旧 API 如仍使用，只作为唯一领域服务的兼容门面，不复制业务逻辑。
- 旧页面授权映射到目标页面前必须验证不扩大权限。
- 详情深链接继续支持；已发布工资条和合同历史保持可访问。

#### 状态兼容

- 现有 Payroll 状态值继续可读；新增发布/发放正交状态时，历史 `PUBLISHED/PAID/CLOSED` 映射到对应标志。
- 旧更正批次保留原 delta 和工资条；新更正使用累计基线规则。
- 旧付款/税务凭证继续保留，不因新状态模型丢失。

#### 部署和验收环境

- `DatabaseSeeder` 不默认加载 demo。
- `hrms:install` 默认只建必要元数据、唯一管理员和空业务表；具体公司假期、工资、税费后置配置。
- demo 只通过显式 dev/test 命令在隔离数据库加载；生产拒绝 demo/reset。
- `iam:sync-capabilities` 改为增量 upsert，保留自定义角色与页面。
- Compose 启动前生成 APP_KEY、执行迁移和安装验证。
- 健康检查校验迁移、安装状态和管理员状态。
- 升级执行前向迁移、权限目录同步、数据核对、备份恢复验证。
- MCP 验收使用 MySQL/Redis/对象存储真实栈，不以 SQLite 或 mock 作为最终证据。

## 6. 风险

### 风险 1：工资双事实源导致历史与现状金额不一致
- **原因：** `employment_terms`、`employee_compensations` 和合同约定均可表达工资。
- **影响：** 迁移后可能按错误金额计薪，历史与未来报表不一致。
- **处理：** 以 Requirement 定义唯一执行源；旧字段只读；迁移冲突阻断；新旧引擎并行 golden 对账通过后切换。

### 风险 2：规则引擎发布错误影响大批员工
- **原因：** 用户可配置条件、阶梯、比例、依赖和舍入。
- **影响：** 一个发布错误可在多员工、多批次造成错发。
- **处理：** 草稿/验证/试算/影响预览/发布/退役、版本不可变、依赖和类型校验、发布权限和审计、发布前标准用例。

### 风险 3：时间事实不完整或重复
- **原因：** 请假、打卡、加班、出差、补卡、月结、撤销来自不同入口。
- **影响：** 多发、少发、重复扣、跨月错误。
- **处理：** 统一 Time 事实版本、按日/区间来源唯一、净额计算、冻结 hash、月结和工资快照绑定、冲突阻断。

### 风险 4：审批效果重复执行或状态不同步
- **原因：** Workflow、业务状态和 Effect 是三个状态源。
- **影响：** 批准后未执行、重复执行、页面与实际业务不一致。
- **处理：** 统一 Effect Handler、状态投影、唯一执行键、重试幂等、失败可见和业务状态回写。

### 风险 5：权限模型迁移导致越权或业务不可用
- **原因：** 页面、动作、锚点、数据范围和字段策略当前不一致。
- **影响：** 员工读他人工资、标准角色无法审批、撤权后旧页签仍能写。
- **处理：** 单一页面动作目录、原子角色保存、统一 effective roles/auth_version、对象级 allowed_actions、真实负测和撤权测试。

### 风险 6：工资批次并发与长事务
- **原因：** 批次计算、审批、更正、发放可能并发；试算可能涉及大量员工。
- **影响：** 重复计算、重复发放、锁等待和超时。
- **处理：** 批次/员工级唯一键、行锁、异步计算、逐人事务、只重试失败员工、长任务不占请求事务。

### 风险 7：更正和 YTD 难以回滚
- **原因：** 更正、已支付工资、累计税额和跨年累计互相影响。
- **影响：** 重复支付、税累计错误、历史报表不可信。
- **处理：** signed YTD ledger、累计基线、原工资条不可覆盖、更正独立批次、golden case 和真实数据库对账。

### 风险 8：历史迁移存在无法自动判断的数据冲突
- **原因：** 旧合同、Terms、薪酬档案、假期类型和历史状态可能缺关联或重叠。
- **影响：** 自动回填造成错误绑定和历史漂移。
- **处理：** unresolved 数据、冲突清单、阻断员工/批次，不自动取第一条或按金额猜测；人工裁决留痕。

### 风险 9：报表和导出泄漏薪资或使用旧投影
- **原因：** 薪酬投影不可用，图表和导出权限不完整。
- **影响：** 未授权金额泄漏，管理层依据错误数据决策。
- **处理：** 真实 PayrollCostDirectory、投影版本/时点、字段级裁剪、导出重新鉴权、汇总明细对账。

### 风险 10：生产初始化和升级破坏现有数据
- **原因：** 默认 Seeder、安装器、权限同步和 Compose 路径不一致。
- **影响：** 新库加载 demo，旧库丢失自定义角色或业务配置。
- **处理：** 默认无 demo、安装状态检查、upsert 同步、升级快照/校验和/恢复演练、生产拒绝 reset。

### 风险 11：MCP 验收被 mock、旧测试或不稳定环境误导
- **原因：** 前端默认 mock，旧测试路径失效，登录限流和演示账号依赖环境变量。
- **影响：** 页面“全绿”但不能证明真实业务闭环。
- **处理：** 强制真实 HTTP 模式、干净迁移环境、固定验收账号策略、串行 MCP、每动作保存证据、缺失数据标 BLOCKED。

### 风险 12：21 模块范围过大导致半闭环上线
- **原因：** 依赖链长，页面、数据、权限和下游同时变化。
- **影响：** 半新半旧、状态不一致、验收无法签收。
- **处理：** 按模块依赖和业务闭环分批实施，只设一个正式生产验收口；模块未完成下游消费和权限负测不得标记完成。

## 7. 技术方案摘要

```text
核心设计：
- 保留模块化单体和现有权限、Workflow、Money、快照、审计、Outbox、Element Plus 基础。
- 用“合同约定版本 + Payroll 执行薪酬版本 + 方案/规则版本”替代工资双源和单批次单方案。
- 用“Time 标准事实版本 → Payroll 不可变快照 → 精确计算 → 复核/审批 → 发布/发放 → 更正/YTD”形成唯一工资闭环。
- 用对象级 allowed_actions、有效角色、数据范围和字段策略统一前后端权限。
- 用模块级 MCP 人工验收和证据台账决定 GO/NO-GO。

主要变化：
- People/Lifecycle/合同收敛写入口和生效日期。
- Time 打通审批 Effect、净事实、月结快照、加班调休和出差计勤。
- Payroll 支持员工级多方案、规则引擎、合同关联、月中分段、缺项阻断、累计更正和 signed YTD。
- Benefits/Talent 通过受控输入进入 Payroll；Reporting/Notification/Installer 改为真实数据和真实状态。
- 前端补齐管理动作、自助入口、状态同步和精确金额展示。

复用：
- Money/Decimal、Clock/公司业务日期。
- CommandRunner/Idempotency、Audit、Outbox。
- Workflow Case/Decision/Task/Effect。
- CapabilityAuthorizer、AuthorityBinding、AuthorizationSnapshot、FieldSet。
- Payroll 状态机、输入快照、hash、工资条、对账和导出。
- Element Plus 页面壳、表格、表单、状态组件和 Playwright MCP。

新增：
- 员工/合同/组织历史版本与统一生命周期命令。
- 员工执行薪酬版本、规则版本、批次成员和 enriched snapshot v2。
- 时间事实月度版本、调休账本、福利计薪输入、绩效工资映射、培训考试结果。
- YTD signed ledger、更正累计基线、对象级 allowed_actions。
- 统一页面动作能力目录、生产安装状态和真实健康检查。

关键影响：
- 直接影响全部 21 模块，核心阻断在 IAM、People/Lifecycle、Time、Payroll、Benefits、Talent 和 Reporting。
- 所有工资、合同、假勤、审批、报表、导出和员工自助页面都要重新核对上下游。
- 历史数据迁移、真实 MySQL 栈和 MCP 人工验收是上线前置条件。

风险：
- 工资双源和规则错误可能导致批量错发。
- Time 净事实、审批 Effect、并发计算和更正累计最易出错。
- 权限锚点、角色版本、字段裁剪和导出遗漏会造成数据泄漏。
- 历史迁移冲突必须阻断、留痕和人工裁决。
- 不能用 mock、自动测试或静态检查替代真实 MCP 验收。
```
