# FactoryHR V2.3 M20｜审批流程中心 — 详细实施计划
> **状态：Proposed — 待用户确认。** 本计划不得在规格批准前执行。
> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.
**Goal:** 将 `/workflow` 收敛为“我的待办 / 我发起的 / 我审批的 / 模板设置”四视图，详情稳定深链 `/workflow/cases/:id`；保证只有真实待办分派人（或显式合规委派/管理员带理由覆盖）能作出决定，重复决定幂等，业务效果失败可见且可重试。
**Architecture:** `Workflow` 独占 `workflow_templates`、`cases`、`workflow_instances`、`workflow_tasks`、`decisions`、`effects`、`case_events`。业务模块只提供受限 effect handler 与 read port，Workflow 不写业务表。`GET /v1/cases` 继续支持 `view=my_approvals|my_requests|my_decided`；模板列表/创建使用现有 `GET/POST /v1/workflow/templates`。前端只保留 `/workflow` 与 `/workflow/cases/:id`，审批按钮只在服务端返回 `is_awaiting_me` 或显式管理员覆盖上下文时显示。
**Tech Stack:** Laravel 13 / PHP 8.3 / MySQL 8.4 / Vue 3.5 / TypeScript / Element Plus / PHPUnit / Vitest / Playwright / OpenAPI 3.1。
## Global Constraints
- 规范优先级：用户裁决 > 本计划 > V2.3 M20 模块规格 > V2.1 设计 > 历史文档。
- `/workflow` 与 `/workflow/cases/:id` 为唯一入口，不新增侧栏审批页；不保留旧 `/cases` 调试页面作为业务入口。
- 决定只能由该节点 `PENDING` 任务的 `assignee_user_id` 执行；委派需有效委派记录；管理员覆盖必须 `workflow.case.admin` + ≥10 字理由；其他用户统一 404。
- 重复决定使用幂等键返回原决定，不重复写业务效果；效果失败保留 `FAILED` 与尝试次数，重试端点不得重复 `Decision`。
- 审批结果与业务单据事实分离：`application_status` 与 `effect_status` 分开显示；未生效必须可见。
- 未执行测试、E2E、迁移演练写 `NOT RUN`，不得写“通过”。

### 1.3 当前缺陷
1. `frontend/src/modules/platform/pages/WorkflowCenterPage.vue` 默认 `view: 'all'`，视图顺序为待办/已处理/我发起/全部可见；与目标“我的待办/我发起/我审批的/模板设置”不一致，且没有模板视图。
2. 列表与详情把 `requester_user_id` 显示为 `用户 #id`（`WorkflowCenterPage.vue` 的 `requester` 列、`WorkflowCaseDetailPage.vue::actorText()`）；业务详情无法识别申请人、审批人、被代理人。
3. `frontend/src/modules/platform/api/index.ts::decideWorkflowCase()` 只发送 `{action, comment}`，不透传管理员覆盖理由；详情页 UI 无管理员覆盖说明，后端 `DecisionService::resolveActingGrant()` 已支持 `reason` 与委派（**不重写**）。
4. 详情页只显示 effect 状态与时间线，没有失败效果列表与重试按钮；`POST /v1/effects/{id}/retry` 与 `backend/app/Modules/Workflow/Http/Controllers/EffectController.php` 已存在且要求 `workflow.case.admin` + reason，前端未接线。
5. `frontend/src/views/CaseCenterView.vue` 仍保留旧 `/cases`、`/cases/:id` 调试/兼容页面并实现 `retryCaseEffect(detail.value.id)`（把 **case_id** 传给 effect retry，语义错误）；不得以该页面作为业务入口。
6. `backend/app/Modules/Workflow/Services/CaseQueryService.php` 只返回 `requester_user_id`，不返回申请人/审批人显示名；直接添加前端拼接中文名会形成跨模块读取，应由 IAM `UserAudienceDirectory::displayName()` 在 Workflow 投影内注入只读显示名。
7. 后端 `GET /v1/cases` 未校验 `view` 枚举；未知 `view` 静默退回可见集合，前端拼错参数会看到“全部”，必须 422 `INVALID_CASE_VIEW`。
## 2. 目标契约
### 2.1 页面结构
```text
/workflow
├── Tab/分段：我的待办 | 我发起的 | 我审批的 | 模板设置
├── 筛选：类型、状态、业务日期；分页由服务端执行
├── 列表列：案例编号、事项类型、申请主题、申请人、申请状态、生效状态、当前环节、时限、操作
└── 详情链接 -> /workflow/cases/:id
/workflow/cases/:id
├── 摘要：申请人、申请对象、业务摘要、业务日期
├── 审批链/历史：节点、处理人、决定、意见、委派/覆盖标记
├── 证据：时间线事件与结构化 payload（只展示白名单字段）
├── 决定区：仅当 is_awaiting_me 时显示同意/驳回/退回；管理员覆盖需理由
└── 生效区：effect_status、每个 effect 的状态/尝试次数/错误摘要；FAILED 时管理员可重试
```
六态：`loading | empty | unconfigured | forbidden | error | success`；`unconfigured` 用于无模板、无当前节点、effect 未调度；`partial` 用于任务/时间线降级。
### 2.2 DTO / API
| 操作 | 状态 | Capability | 契约 |
|---|---|---|---|
| `GET /v1/cases?view=my_approvals\|my_requests\|my_decided` | 现有，补校验 | `workflow.case.read` | 未知 view 422 `INVALID_CASE_VIEW`；返回申请人显示名与 `is_awaiting_me` |
| `GET /v1/cases/{id}` | 现有 | `workflow.case.read` | 仅 requester/task assignee/decision actor/admin 可见；越界 404 |
| `GET /v1/cases/{id}/timeline` | 现有 | `workflow.case.read` | application/effect 分列；决定人、被代理人、覆盖理由可见 |
| `POST /v1/cases/{id}/decisions` | 现有，客户端补 reason | `workflow.case.decide` | `{action, comment, reason, target_user_id}`；非指派 404；管理员覆盖需 ≥10 字理由 |
| `POST /v1/cases/{id}/withdraw`、`submit` | 现有 | `workflow.case.create` | 仅请求人；状态机校验 |
| `GET /v1/tasks/my` | 现有 | `workflow.case.read` | 当前用户 `PENDING` 任务和 SLA；不返回他人任务 |
| `GET /v1/workflow/templates` | 现有 | `workflow.case.read` | 模板版本列表 |
| `POST /v1/workflow/templates` | 现有 | `workflow.case.admin` | 创建新版本；同 company+code+version 幂等 |
| `POST /v1/effects/{id}/retry` | 现有，前端接线 | `workflow.case.admin` | `{reason}` ≥10 字；同 effect 幂等；成功 APPLIED，失败 202/FAILED |
| `GET /v1/access-review` | 现有 | `iam.audit.read` | 只由审计模块消费，不进入审批业务页 |
### 2.3 状态机与主体
```text
Case：DRAFT -> SUBMITTED -> IN_REVIEW -> APPROVED/REJECTED/WITHDRAWN/CANCELLED
Effect：SCHEDULED -> APPLIED；SCHEDULED -> FAILED -> (retry) APPLIED/FAILED
决定：APPROVE/REJECT/RETURN；同幂等键重放返回原决定
委派：有效期内 -> principal 待办被代理 -> 记录 delegation_id
管理员覆盖：仅 workflow.case.admin + reason >= 10 字 -> 记录 admin_override=true
```
`actor_user_id` 是实际提交人；`requester_user_id` 是申请人；`approver_user_id` 是节点指派人；委派时记录 `on_behalf_of_user_id` 与 `delegation_id`。前端不提交 `requester_user_id`/`approver_user_id`，显示名由后端投影返回。
### 2.4 权限与字段
- 页面进入 `workflow.case.read`；决定 `workflow.case.decide`；模板创建/效果重试 `workflow.case.admin`。
- 列表/详情只显示当前用户可见案例；非指派决定 404；撤销权限后旧标签页提交必须 403/404。
- 业务摘要只呈现白名单字段（金额整数分转元、日期按公司时区）；不得输出原始 payload JSON、PHP 类名、堆栈或 effect handler 类名。
- 决定理由/意见 P1；薪资、Offer、福利等业务金额沿用原模块字段档位；工作流投影不得放宽原模块 P3。
