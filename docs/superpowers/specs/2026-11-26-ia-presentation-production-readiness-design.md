## 1. 结论先行

五个现象不是五个可以分别“补样式、改文案”的页面缺陷，而是同一套交付模型失真的五种表现：

| # | 用户现象 | 直接原因 | 本质原因 |
|---|---|---|---|
| 1 | 多个业务板块共用一个 Tab 条 | `PeopleWorkspace` 在员工页面内硬编码“员工档案 / 部门管理 / 岗位管理 / 员工异动 / 劳动合同” | **导航被实现了两次**：全局侧栏已表达模块边界，页面内又用跨模块 Tab 重新拼装；页面身份没有绑定到“用户任务” |
| 2 | 员工 CURD 被拆成多个页面，详情无入口 | 实施书把 `create`、`:id`、`:id/education`、`:id/files` 等“视图/动作”逐条登记为页面；注册表原样照搬，左侧菜单也原样展示 | **页面与视图/动作的粒度混淆**；交付门禁奖励页面数量，不奖励任务闭环 |
| 3 | 列表显示 `ACTIVE`、`FULL_TIME`、`MINOR_UNITS` | `rowText()` 只做通用对象投影，不翻译稳定枚举；部分页面直接渲染 `rowText(status)` 或原始单位 | **缺少“机器码 → 中文展示”的单一词典边界**；展示层与接口契约直接耦合 |
| 4 | 页面出现“字段档位与可导出口径均由 GET /v1/... 返回” | 页面描述直接写接口路径、表名、字段档位、实现缺口 | **把工程可追溯性放进了用户界面**；缺少“面向用户文案”和“面向运维信息”的分层 |
| 5 | 系统管理页无样式、创建/编辑不是弹窗 | 页面外壳使用全局 `page-header/panel`，内部却用裸 `table/input/select/details`；`PlatformWorkspace` 的样式是 `scoped`，独立页面无法继承；创建表单直接铺在列表下方 | **存在两套平行的 UI 实现**；没有“统一页面骨架 + 弹窗表单”的强制契约，视觉评审和组件复用没有进入发布门禁 |

**总根因：**

> 项目把“注册了页面码、接了接口、门禁变绿”误当成“用户任务完成”。页面注册表、菜单、权限、组件、文案和验收六者之间只有单向字符串匹配，没有围绕“一个用户任务一个工作区”的双向约束。于是系统能证明“有 160 个条目”，却不能证明“用户能在一个地方完成一件事”。

这意味着不能继续逐页打补丁。必须先裁决页面模型，再统一展示层，最后重写门禁；否则每修一页都会复制同样结构，每加一个模块都会继续产生新的跨模块 Tab、裸控件和英文状态。

## 2. 事实基线

### 2.1 实施书本身已经给出正确方向

V1.1 实施书并非没有产品规范，冲突主要来自“规范被逐条页面清单覆盖”。

| 来源 | 已有要求 | 与现状的关系 |
|---|---|---|
| §03A.5 员工档案 | 员工列表、新增、档案详情、教育、经历、附件、变更审批、导入校验 | **把视图和动作登记成“功能页面”**，是页面碎片的直接来源 |
| §09.1 | 查看/编辑面板拆分为可复用表单和详情组件 | 方向正确，但没有规定弹窗/页面的选择规则 |
| §09.2 员工档案 | 顶部筛选、导入导出、表格、**员工详情抽屉** | 与本次用户裁定的“列表 + 独立详情页”冲突，需 ADR 裁决 |
| §09.2 部门管理 | 左侧部门树、右侧详情和员工列表 | 说明同一模块应采用工作区而不是跨模块 Tab |
| §09.2 角色管理 | 基础信息 + 资源树 + 操作矩阵 + 数据范围 + 字段权限 + 用户 | 角色页应是单一治理工作区，而不是多个独立菜单 |
| §13.4 | 每个截图菜单需列表、创建/编辑/动作、持久化、权限、空错态、审计、E2E | 验收对象是“菜单闭环”，不是“每个子视图一条路由” |

### 2.2 路由和组件现状

以基线 `3aa719e` 为准：

- `frontend/src/router/registry.ts` 注册 160 条页面。
- `frontend/src/modules/people/pages/index.ts` 为 People 域映射 39 个页面组件。
- 39 个 People 页面中，大多数只是对 `PeopleWorkspace` 的薄包装：仅传入不同的 `config`。
- 员工域 11 个条目共享同一套 `PeopleWorkspace` 业务分支：
  - `hr/employees/index`
  - `hr/employees/create`
  - `hr/employees/by-id`
  - `hr/employees/by-id/education`
  - `hr/employees/by-id/work-history`
  - `hr/employees/by-id/contacts`
  - `hr/employees/by-id/credentials`
  - `hr/employees/by-id/history`
  - `hr/employees/by-id/files`
  - `hr/employees/by-id/changes`
  - `hr/employees/imports`

这解释了为什么“页面文件唯一”门禁会通过，但用户体验仍是一个被切碎的工作区：唯一性只存在于文件名，业务分支仍在共享壳内。

### 2.3 页面内跨模块导航

`PeopleWorkspace.vue` 硬编码了五个模块入口：

```text
员工档案 / 部门管理 / 岗位管理 / 员工异动 / 劳动合同
```

这不是“页面内页签”，而是第二套全局导航。它带来三个直接后果：

1. 用户在“员工列表”看到与员工无关的部门、岗位、异动、合同入口。
2. 全局侧栏和页面内 Tab 对“当前模块”给出两套状态，键盘与读屏用户会遇到重复导航。
3. 每个 People 页面都必须依赖其他模块的文案和路由，页面边界无法独立演进。

### 2.4 兜底页与平台页的平行实现

- `ResourcePage.vue` 在无成熟视图时回退为“取第一条对象的键名作为列头、直接 `String(value)` 渲染”。这正是英文枚举、原始字段名和调试式说明进入界面的通道。
- `SystemUsersPage.vue` 和 `SystemRolesPage.vue` 是独立页面，但内部使用裸 `table`、`input`、`select`、`details`。
- `PlatformWorkspace.vue` 中定义了大量 `platform-*` 样式，但样式块是 `scoped`；独立 System 页面既没有导入这些样式，也没有使用 Element Plus 表单/表格组件。
- 结果是“有组件库却无样式”：不是 Element Plus 不可用，而是页面绕过了它。

### 2.5 发布门禁奖励了错误目标

现有门禁主要验证：

- 160 条注册表条目存在；
- 每个 `componentKey` 有唯一 `.vue` 文件；
- 每页声明 `requiredApis`、`states`、`negativeTests`；
- 每个 API 有 capability。

这些检查都必要，但都不能回答：

- 这个页面是否对应一个完整用户任务？
- 列表页是否能完成本对象的创建、查看、编辑、归档？
- 页面是否出现跨模块导航？
- 是否直接渲染英文枚举、接口路径、表名、字段档位或实现缺口？
- 创建/编辑是否使用了统一弹窗表单？
- 列表是否复用了统一表格、空态、错误态和分页？

因此会出现“160/160 成熟视图、真实栈通过，但截图仍不可用于生产”的悖论。

## 3. 第一性原理：页面、视图、动作、权限分别是什么

### 3.1 四个概念必须分开

| 概念 | 定义 | 是否进侧栏 | 是否独立路由 | 权限粒度 |
|---|---|---:|---:|---|
| **模块（Module）** | 一组围绕同一业务对象的能力，如员工、部门、角色 | 作为分组 | 否 | 不直接授权 |
| **页面（Page）** | 用户完成一个主要任务的工作区，如员工列表、员工详情 | 是（仅主入口） | 是 | `page_code` |
| **视图（View）** | 页面内部的展示形态，如详情概览、教育经历、附件 | 否 | 仅深链 | 复用页面权限 + 区域能力 |
| **动作（Action）** | 创建、编辑、归档、恢复、导入、导出、分配角色 | 否 | 否 | 动作能力码 |

**本质判断：**

- 页面是“任务容器”，不是“字段分组”。
- 视图是“容器内的信息组织”，不应单独成为菜单。
- 动作是“对对象的状态变更”，应使用弹窗、抽屉或确认对话框，而不是新页面。
- 权限必须按“进入页面”和“执行动作”分开，不能靠页面数量推导。

### 3.2 员工模块的目标模型

经用户裁定，采用“列表 + 独立上下文详情页”：

```text
/hr/employees                  员工工作区（列表、筛选、新建、归档、恢复、版本化任职/条款维护）
/hr/employees/:id              员工详情（概览、任职、经历、联系人、证照、履历、附件、变更）
```

约束：

- `/hr/employees` 是唯一菜单入口。
- `/hr/employees/:id` 是隐藏的上下文路由，不出现在侧栏；从列表行、搜索结果、通知、审批单进入。
- 详情页内的区域通过页签或锚点切换，不新增顶级菜单。
- 新增、归档、恢复、子档案编辑均使用弹窗/抽屉/确认对话框。
- 详情页必须支持 `?tab=education` 等深链，但该参数不能成为独立 `page_code`，也不能单独授予权限。
- 删除采用归档；归档后详情仍可按权限查看历史，恢复是独立动作能力。
- 当前没有员工主档 PATCH；主档“编辑”通过追加任职/条款版本或既有异动接口完成。
- 当前没有员工级批量导入/导出端点；补口前不展示可点击的导入/导出按钮。

### 3.3 页面内 Tab 的合法与非法边界

**合法：**

- 同一对象内部的视图切换：概览 / 任职 / 经历 / 附件 / 变更。
- 同一治理任务内部的视角切换：页面权限 / 按钮权限 / 数据范围 / 字段权限。
- 同一报表的图表 / 明细切换。

**非法：**

- 员工页面出现部门管理、岗位管理、员工异动、劳动合同入口。
- 部门页面出现员工、岗位、合同入口。
- 任何页面用 Tab 代替全局导航。

判定规则：

> Tab 的两端必须是“同一个业务对象、同一个用户任务、同一套数据范围”；跨对象、跨模块、跨权限域的切换必须回到全局导航。

### 3.4 页面粒度的判定规则

一个条目可以成为独立页面，当且仅当同时满足：

1. 有独立的用户任务和成功标准；
2. 有独立的入口和返回上下文；
3. 可以独立授予页面权限而不造成任务断裂；
4. 有独立的数据读取和至少一个动作，或明确的只读价值；
5. 不依赖另一个页面的局部状态才能理解。

不满足时，应降级为：

- 同一页面的视图/Tab；
- 弹窗/抽屉表单；
- 行内动作；
- 批量任务结果面板。

按此规则，员工模块的 11 个条目应收敛为 2 个页面 + 若干视图/动作。

### 3.5 导航的唯一职责

全局导航只回答两个问题：

1. 我现在在哪个模块？
2. 我还能去哪些模块？

页面内导航只回答：

1. 我在这个对象的哪个信息区域？
2. 这个对象还有哪些相关信息？

两者不能互相替代，也不能重复表达同一层级。

## 4. 跨领域类比与方案比较

### 4.1 类比

| 领域 | 做法 | 对本项目的启示 |
|---|---|---|
| 操作系统/IDE | “项目/文件/编辑器”三层；打开文件不改左侧项目树 | 页面是工作区，详情是上下文，不应把每个字段页塞进菜单 |
| 电商后台 | 商品列表 + 商品编辑抽屉/详情页；订单列表 + 订单详情 | CRUD 属于同一对象工作区，创建/编辑用弹窗或抽屉 |
| 银行核心系统 | 客户主数据 + 关系视图；交易动作有独立权限码 | 页面权限与动作权限分离；审计与数据范围独立 |
| 医疗 EHR | 患者时间线 + 分区视图；跨患者导航靠全局搜索 | 复杂对象详情用页签组织，不用跨对象 Tab |
| 航空运行控制 | 单一任务工作台 + 检查单；危险动作二次确认 | 高后果动作不能藏在子页面；确认与审计是流程一部分 |
| 设计系统 | Token → Primitive → Pattern → Page 四层 | 页面不得绕过 Primitive 直接拼裸控件 |

### 4.2 三个可选方案

| 方案 | 描述 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A. 保留全部路由，只修样式和文案 | 每个子页面继续存在，补中文、补 CSS | 改动最小 | 页面碎片、跨模块 Tab、权限膨胀仍在；维护成本持续增长 | 拒绝 |
| B. 全部收敛为一个超长页面 | 所有 CRUD 和详情塞进列表页 | 入口最少 | 信息密度过高、深链与权限不可控、移动端不可用 | 拒绝 |
| C. 列表工作区 + 独立详情页 + 弹窗动作 | 菜单只留列表；详情为隐藏上下文路由；创建、归档、恢复、子档案编辑用弹窗 | 任务闭环、权限清晰、可深链、可测试、可扩展 | 需要重排路由、权限、菜单和测试；迁移工作量大 | **推荐** |

**推荐理由：**

- 符合用户已裁定的“列表 + 独立详情页”。
- 保留详情页的深链、打印、审计和复杂信息组织能力。
- 将创建/编辑从路由中移除，消除“新增员工”作为独立菜单的荒谬感。
- 允许后续把详情页内的信息区做成可复用视图，而不增加页面码。

## 5. 目标设计

### 5.1 信息架构

#### 5.1.1 菜单层级

```text
工作台
组织与人事
├─ 员工档案
│  └─ 员工列表（唯一菜单入口）
├─ 部门管理
│  └─ 组织架构（唯一菜单入口）
├─ 岗位管理
│  └─ 岗位目录（唯一菜单入口）
├─ 员工异动
│  └─ 异动台账（唯一菜单入口）
└─ 劳动合同
   └─ 合同台账（唯一菜单入口）
```

说明：

- “员工异动”下的入职、转正、调岗、调薪、借调、离职不再各自成为菜单，而是异动台账的“发起异动”动作类型。
- “劳动合同”下的录入、续签、变更、终止、模板不再各自成为菜单，而是合同台账的动作和筛选视图。
- “部门管理”下的列表、编辑、成员、迁移、编制收敛为组织架构工作区的视图/动作。
- “岗位管理”下的编辑、编制、资格、职级、任职人员收敛为岗位目录工作区的视图/动作。

#### 5.1.2 员工页面模型

```text
/hr/employees
├─ 顶部：页面标题 + 业务说明 + 新建员工
├─ 筛选：关键词、组织、状态、as-of 日期
├─ 工具栏：列设置、刷新（导入/导出待后端补口后启用）
├─ 表格：工号、姓名、组织、岗位、状态、入职日期、操作
├─ 行操作：查看、归档/恢复
├─ 空态/加载/错误/无权限
└─ 弹窗：新建员工、归档确认、恢复确认

/hr/employees/:id
├─ 头部：姓名、工号、状态、组织/岗位、返回列表
├─ 概览：基本信息、当前任职、合同摘要、直属经理
├─ 页签：概览 / 任职与合同 / 教育经历 / 工作经历 / 联系人 / 证照 / 履历 / 附件 / 变更
├─ 区域动作：新增/编辑教育经历、上传附件、发起变更、追加任职/条款版本
└─ 弹窗：区域表单、敏感字段查看目的、归档/恢复
```

约束：

- 当前后端没有员工主档 PATCH 端点；“编辑”通过追加任职/条款版本或既有异动接口完成，不能伪造 PATCH。
- 当前没有员工级批量导入/导出端点；在补口完成前，工具栏不得出现可点击的假入口。
- 员工详情采用独立页，不是抽屉；这是本次用户裁定，覆盖 V1.1 §09.2 的旧表述。

#### 5.1.3 系统管理页面模型

```text
/system/users
├─ 用户列表（统一表格）
├─ 新建用户（弹窗）
├─ 行操作：查看权限预览、分配角色、停用/启用
└─ 分配角色（弹窗/抽屉）

/system/roles
├─ 角色列表（左栏或顶部选择）
├─ 授权工作区（右侧）
│  ├─ 页面权限
│  ├─ 按钮权限
│  ├─ 数据范围
│  └─ 字段权限
├─ 保存前差异预览（对话框）
└─ 角色复制/新建（弹窗）
```

### 5.2 路由与页面码

#### 5.2.1 保留为独立页面的条目

- 列表/工作区页：每个业务对象一个。
- 详情页：`/:id` 作为隐藏上下文路由。
- 只读治理页：角色、用户、菜单、权限、数据范围、字段策略等，各自一个工作区页面。

#### 5.2.2 降级为视图/动作的条目

- `create`、`editor`、`new` 等动作型路由。
- `:id/education`、`:id/work-history`、`:id/contacts`、`:id/credentials`、`:id/history`、`:id/files`、`:id/changes` 等详情子视图。
- `movements/onboarding|probation|transfer|salary-change|secondment|offboarding` 等异动类型。
- `contracts/editor|renewals|changes|templates` 等合同动作。
- `imports`、`export` 目录不是“页面”的同义词：只有在后端存在独立任务列表或结果查询时才保留为视图；当前员工导入批次没有跨员工聚合端点，因此不注册为顶级页面。

#### 5.2.3 兼容与重定向

- 旧 URL 不直接 404，保留 301/302 到新工作区，并带上 `action` 或 `tab` 查询参数。
- 旧页面码保留一个发布周期的弃用映射，但不再出现在菜单和授权矩阵中。
- 迁移期必须同时支持“旧页面码 → 新页面码”的授权映射，避免已授权角色突然失效。

### 5.3 权限模型

#### 5.3.1 页面与动作分离

- `page_code`：控制能否进入工作区/详情页。
- `action capability`：控制创建、编辑、归档、恢复、导入、导出、分配角色等。
- `detail tab`：不单独授权；由页面权限 + 区域数据能力共同决定。

#### 5.3.2 详情页的权限

- 能进入 `/hr/employees/:id` 的前提是拥有员工页面权限，并且后端对该员工返回可见。
- 详情子区域不新增页面码；敏感区域（如附件、变更、薪资）由动作能力或字段档位控制。
- 无权限时返回 404 而非 403，避免泄露记录存在性。

#### 5.3.3 菜单与路由

- 菜单只展示主工作区页面。
- 详情页 `menu: null`，不进入侧栏。
- 路由守卫仍校验 `page_code` 与动作能力。
- 页面内的按钮通过 `Can`/`ActionGate` 渲染，但后端仍是唯一授权真相。

### 5.4 展示层统一契约

#### 5.4.1 页面骨架

所有业务页面必须使用同一套骨架：

```text
PageShell
├─ PageHeader（标题、说明、主操作）
├─ FilterBar（可选）
├─ ContentPanel
│  ├─ DataTable / DetailTabs / FormSection
│  └─ Loading / Empty / Error / Forbidden
└─ Dialogs（创建、编辑、导入、确认）
```

禁止：

- 页面内直接写 `<table>`、`<input>`、`<select>`、`<details>` 作为主要布局。
- 页面内重复实现分页、空态、错误态、加载态。
- 页面内出现第二套全局导航。

#### 5.4.2 表格

统一使用 `DataTable` 或同一抽象层，至少支持：

- 列定义与中文表头；
- 服务端分页；
- 搜索与筛选；
- 加载骨架；
- 空态与下一步动作；
- 错误重试；
- 行操作；
- 横向滚动与键盘可访问；
- 批量选择（需要时）。

#### 5.4.3 表单

- 创建/编辑使用 `FormDialog` 或 `FormDrawer`。
- 字段分组按用户语义，不按数据库表。
- 校验在字段旁显示中文错误。
- 提交中禁用重复提交。
- 失败保留用户输入。
- 关闭前检测脏状态。
- 成功后刷新列表或详情，并给出业务后果提示。

#### 5.4.4 详情

- 详情页使用统一 `DetailHeader` + `DetailTabs`。
- 每个区域有独立的加载/空/错误态。
- 敏感字段使用 `MaskedField`，查看需填写目的并记录审计。
- 变更历史使用 `Timeline`，区分申请/生效/系统轨道。

### 5.5 文案与字典

#### 5.5.1 三层文案

| 层级 | 面向对象 | 示例 | 位置 |
|---|---|---|---|
| 业务文案 | 最终用户 | “在职”“全职”“固定期限合同” | 页面、表格、表单 |
| 技术标识 | 管理员/审计 | `ACTIVE`、`FULL_TIME`、能力码 | 审计详情、开发者工具、权限矩阵的技术列 |
| 运维信息 | 运维/支持 | 请求编号、接口路径、字段档位 | 错误详情折叠区、日志、支持包 |

规则：

- 主界面不出现接口路径、表名、字段档位、数据库键名。
- 技术标识只在管理员明确进入“技术详情”时显示。
- 错误提示先给用户可执行的下一步，再在折叠区给请求编号。
- 空态说明“为什么为空、下一步做什么”，不解释后端实现。

#### 5.5.2 字典单一来源

建立前端共享字典：

```ts
// frontend/src/shared/domain/labels.ts
export const EMPLOYEE_STATUS_LABEL = { ACTIVE: '在职', ... }
export const EMPLOYMENT_TYPE_LABEL = { FULL_TIME: '全职', ... }
export const ASSIGNMENT_TYPE_LABEL = { PRIMARY: '主任职', ... }
export const CONTRACT_TYPE_LABEL = { FIXED_TERM: '固定期限', ... }
export const METRIC_UNIT_LABEL = { COUNT: '人', MINOR_UNITS: '元', ... }
export const ANCHOR_TYPE_LABEL = { SELF: '本人', ORG_UNIT: '本部门', ... }
```

约束：

- 页面不得直接渲染稳定枚举值。
- 新增枚举必须同时新增中文标签和测试。
- 未知枚举显示“未知状态”并记录开发告警，不直接显示原始码。
- 金额单位 `MINOR_UNITS` 不应出现在用户界面；金额用 `MoneyText` 格式化。

#### 5.5.3 文案门禁

- 扫描页面模板中的 `GET /v1/`、`POST /v1/`、`role_pages`、`field_profile`、`tenant_id`、`legal_entity_id`。
- 扫描裸枚举：`ACTIVE`、`FULL_TIME`、`MINOR_UNITS` 等出现在可见文本节点。
- 扫描“尚未实现”“计划路径”“实时接口”“演示”“demo”等实现状态文案。
- 允许清单只用于管理员技术详情，并必须显式标注。

### 5.6 系统管理页重建

- `/system/users`：
  - 使用 `PageHeader` + `DataTable` + `FormDialog`。
  - 列表列：用户名、邮箱、状态、角色、MFA、最后登录、操作。
  - 新建用户弹窗：用户名、邮箱、初始密码、是否特权账号。
  - 行操作：权限预览、分配角色、停用/启用。
  - 权限预览使用抽屉或对话框，展示有效页面、动作、拒绝原因。
- `/system/roles`：
  - 角色选择 + 授权工作区。
  - 四个 Tab 使用 Element Plus 的 `el-tabs` 或统一 Tabs 组件。
  - 页面权限使用分组树/复选列表。
  - 按钮权限、数据范围、字段权限使用结构化表格。
  - 保存前差异预览使用 `el-dialog`。
  - 技术标识放在“技术详情”折叠区，不作为主说明。

### 5.7 门禁重写

#### 5.7.1 新增产品级门禁

1. **任务闭环门禁**：每个主工作区页面必须声明 `primaryObject`、`list`、`createAction`、`detailRoute`、`editAction`、`archiveAction`（如适用）。
2. **导航单一性门禁**：页面组件不得包含跨模块导航数组；全局导航只能来自注册表。
3. **详情路由门禁**：`/:id` 详情路由必须 `menu: null`，且从列表有可达入口。
4. **展示原语门禁**：页面模板不得直接使用裸 `table/input/select/details` 作为主布局；必须使用共享组件或 Element Plus。
5. **文案门禁**：禁止接口路径、表名、字段档位、英文枚举、演示/缺口文案出现在用户可见区域。
6. **弹窗动作门禁**：创建/编辑动作必须由 `FormDialog`/`FormDrawer` 承载，不得注册为页面路由。
7. **页面码收敛门禁**：页面码数量与菜单入口数量必须有明确映射；新增页面码必须说明为什么不能是视图/动作。

#### 5.7.2 门禁与现有检查的关系

- 保留现有 capability、OpenAPI、模块边界、页面唯一性检查。
- 新增门禁不能替代现有检查，而是补上“产品可用性”维度。
- 门禁失败必须给出可操作的文件和行号，不允许只报计数。
- 门禁本身要有单元测试，防止规则被绕过。

### 5.8 观测与反馈

- 前端记录页面级错误、空态、慢加载、表单失败、权限拒绝。
- 关键动作记录业务结果，不只记录“成功”。
- 对“用户打开详情后返回列表丢失筛选”这类体验问题，记录返回路径与筛选恢复率。
- 对“用户重复点击创建”记录幂等键命中率。
- 对“用户看到英文枚举”建立前端告警，作为文案门禁的补充。

## 6. 二阶与三阶影响

### 6.1 对用户行为

| 变化 | 二阶影响 | 三阶影响 |
|---|---|---|
| 菜单收敛为对象工作区 | 用户少点几层，任务路径更短 | 需要重新培训；旧书签需重定向；搜索成为主要跨对象入口 |
| 详情改为隐藏路由 | 列表筛选可保留，返回更自然 | 需要统一返回上下文；通知/审批单深链要带来源；浏览器历史要可预测 |
| 创建/编辑改弹窗 | 减少页面跳转和上下文丢失 | 需要处理脏状态、键盘焦点、移动端全屏；复杂表单可能需要分步 |
| 英文枚举改中文 | 用户理解成本下降 | 需要建立字典治理；新增枚举必须有翻译；审计页仍需保留技术码 |
| 技术说明移出主界面 | 页面更干净 | 支持人员需要“技术详情”入口；错误排查不能靠页面文案 |

### 6.2 对系统复杂度

| 变化 | 短期成本 | 长期收益 | 风险 |
|---|---|---|---|
| 页面码收敛 | 需要重排路由、权限、菜单、测试 | 页面数量下降，权限矩阵更小，维护成本降低 | 旧授权映射错误会导致用户突然失去入口 |
| 统一页面骨架 | 需要重建 System/People 页面 | 一处修样式，全站生效 | 统一过度会限制特殊页面；需要明确的 escape hatch |
| 字典集中 | 需要一次性梳理所有枚举 | 文案一致，减少重复 | 字典遗漏会导致“未知状态” |
| 门禁重写 | 需要新增脚本和测试 | 防止回潮 | 门禁过严会阻碍合理例外；需要 allowlist 与 ADR |
| 旧 URL 重定向 | 需要维护映射表 | 保护书签和外部链接 | 重定向链过长；需要监控 404 |

### 6.3 对其他模块的影响

- **部门/岗位/异动/合同**：同样存在“动作被拆成页面”的问题，应复用同一页面模型，不单独打补丁。
- **考勤/请假/加班/出差/薪资**：大量“我的”“台账”“规则”“报表”页面可能也需要区分工作区与视图；先建立判定规则，再逐模块迁移。
- **招聘/培训/绩效**：候选人详情、面试、Offer、培训报名等应以对象工作区 + 视图组织，避免继续复制 `TalentPageShell`。
- **系统管理**：用户、角色、菜单、权限、数据范围、字段策略应统一使用治理工作区模式。
- **报表**：报表目录、运行、导出、订阅是同一报表任务的不同阶段，不应拆成互不相关的页面。

### 6.4 对长期维护成本

**下降的部分：**

- 页面组件数量下降，重复布局和重复权限判断减少。
- 字典、表格、表单、弹窗、状态组件集中维护。
- 门禁能阻止“新增一个字段就新增一个页面”的退化。
- 详情页深链和返回上下文统一，减少用户支持成本。

**上升的部分：**

- 初始迁移需要跨路由、权限、菜单、测试同步修改。
- 需要维护旧 URL 映射和旧页面码弃用周期。
- 需要为复杂详情页设计清晰的区域边界，避免变成新的巨型组件。
- 需要培训管理员理解“页面权限”和“动作权限”的差异。

**净判断：** 短期成本集中在一次性的信息架构迁移；长期成本显著低于继续按页面数量扩张。若不迁移，页面码、菜单、权限、测试会随每个新字段线性增长，最终不可维护。

## 7. 迁移策略

### 7.1 分阶段

| 阶段 | 目标 | 不做什么 |
|---|---|---|
| Phase 0 | 裁决页面模型、详情页形态、旧 URL 策略 | 不改业务逻辑 |
| Phase 1 | 建立共享页面骨架、字典、表格、表单弹窗、详情页组件 | 不一次性迁移所有模块 |
| Phase 2 | 以员工模块为样板完成端到端迁移 | 不扩散到其他模块 |
| Phase 3 | 迁移部门、岗位、异动、合同 | 不改变后端契约 |
| Phase 4 | 重建系统管理页 | 不改变权限内核 |
| Phase 5 | 重写门禁、补 E2E、清理旧页面码 | 不在门禁未绿时宣布完成 |

### 7.2 旧 URL 与旧页面码

- 旧 URL 保留至少一个发布周期。
- 旧页面码映射到新页面码，迁移期授权取并集，避免用户失去入口。
- 迁移完成后删除旧页面码，但保留审计历史。
- 所有重定向必须有 E2E 覆盖。

### 7.3 数据与权限

- 页面码收敛不改变后端数据模型。
- 动作能力码尽量复用现有能力，避免大规模重发授权。
- 需要新增动作能力时，必须同步 OpenAPI、能力目录、角色模板和负测。
- 详情页不新增页面码，避免权限矩阵再次膨胀。

## 8. 验收标准

### 8.1 产品验收

- 员工列表页不再出现部门、岗位、异动、合同入口。
- 员工列表可以完成新建、查看、归档、恢复；进入详情后可维护任职/条款版本和子档案。
- 员工详情有明确入口，支持深链和返回列表。
- 详情页内的教育、经历、联系人、证照、履历、附件、变更不再出现在侧栏。
- 系统用户页和角色页使用统一页面骨架与 Element Plus 组件。
- 创建/编辑/子档案编辑使用弹窗或抽屉，不再作为独立页面。
- 主界面不出现英文枚举、接口路径、表名、字段档位、演示/缺口文案。
- 员工级导入/导出在各自后端契约完成前不显示可点击入口；补口后按同一工作区模式加入。

### 8.2 技术验收

- 页面码与菜单入口的映射有自动化检查。
- 每个主工作区页面有任务闭环声明。
- 页面组件不得包含跨模块导航。
- 详情路由 `menu: null`，列表有可达入口。
- 字典覆盖所有稳定枚举，未知值有兜底。
- 文案门禁通过。
- 旧 URL 重定向 E2E 通过。
- 现有 capability、OpenAPI、模块边界、页面唯一性门禁仍通过。

### 8.3 回归验收

- 直接访问旧 URL 不 404。
- 无权限用户直接访问详情返回 404。
- 撤权后下一次请求立即失效。
- 移动端 360px 宽度可完成员工查看、归档与子档案编辑。
- 键盘可完成列表筛选、打开详情、返回列表、提交表单。
- 屏幕阅读器可识别页面标题、Tab、表格、弹窗和错误提示。

## 9. 风险与未决事项

### 9.1 已裁决

- 员工详情采用“列表 + 独立上下文详情页”，不是抽屉。
- 创建/编辑采用弹窗。
- 页面内只允许同对象视图 Tab。

### 9.2 需要确认

1. 旧 URL 保留周期：一个发布周期是否足够？
2. 详情页是否需要在移动端退化为全屏页面/抽屉？
3. 系统管理页是否允许“高级技术详情”折叠区显示能力码和接口路径？
4. 页面码收敛是否接受一次性权限矩阵重排，还是需要更长的双轨期？
5. 是否在后端补齐员工主档 PATCH，还是正式采用“任职/条款版本化编辑”作为产品语义？
6. 是否在后端补齐员工级批量导入/导出，还是继续只保留单员工导入批次？

### 9.3 明确非目标

- 不在本轮重写后端领域模型。
- 不在本轮改变授权内核（Capability × Anchor × FieldProfile）。
- 不在本轮实现新的业务能力。
- 不在本轮统一所有模块的视觉细节；先建立契约，再逐模块迁移。

## 10. 结论

真正要修的不是五张截图，而是“页面即字段分组、门禁即页面数量”的交付模型。正确顺序是：

1. 用 ADR 裁决页面、视图、动作、权限的边界；
2. 用共享骨架、字典、表格、表单弹窗统一展示层；
3. 以员工模块为样板完成闭环；
4. 再迁移其他模块；
5. 最后用产品级门禁锁住结果。

只有把“用户任务完成”变成可执行的门禁，系统才不会在下一轮继续产生跨模块 Tab、碎片化 CRUD 和英文状态。
